# Change Control

Generated by `prompts/11_IMPLEMENTATION_PLAN_AND_RELEASE_BACKLOG.md`, NO-ASSUMPTION MODE. Defines how
changes to approved scope/contracts/plan are handled once `prompts/12`+ (coding) begins — this
project has 25 Decision IDs, 5 contract documents, and a delivery plan all under explicit approval
gates; coding-phase changes to any of them need the same rigor, not an informal shortcut.

## 1. What counts as a change requiring this process

- Any edit to a `CONFIRMED_CURRENT`/`OUT_OF_SCOPE` Decision ID's resolution in
  `docs/decisions/PRODUCT_DECISION_REGISTER.md`.
- Any edit to an `APPROVED` document under `docs/product/`, `docs/features/`, `docs/ux/`,
  `docs/architecture/`, or `docs/quality/` that changes behavior, scope, or a contract — not a typo
  fix.
- Adding, removing, or re-scoping (`CURRENT`↔`BLOCKED`) a Feature ID.
- Re-sequencing a Feature ID into an earlier wave than `RELEASE_BACKLOG.md` currently places it.
- Answering any item in `docs/product/PRD_OPEN_ITEMS.md` or `FEATURE_QUESTIONS.md` — these are
  pending changes by definition; resolving one **is** a change-control event once it has
  implementation consequences, not just a paperwork update.

## 2. What does NOT require this process

- Implementation-detail decisions consistent with an already-approved contract (e.g. choosing a
  specific error-message string within `API_CONTRACT.md`'s already-approved error shape).
- Bug fixes that restore already-specified behavior.
- Test-case authoring that follows the already-approved `TEST_REWRITE_PLAN.md` patterns.

## 3. Process

1. **Propose:** state the change, the document(s)/Decision ID(s) it touches, and why (a newly
   discovered conflict, a client answer to an open item, a technical infeasibility discovered during
   build).
2. **Impact-check:** identify every downstream document that traces to what's changing — per
   `CLAUDE.md`'s required traceability chain (Evidence → Decision → BRD → PRD → Feature ID → AC →
   UX/Screen → Architecture/DB/API/RBAC/Integration → Test → Code → Release Evidence), a change at
   any link needs its downstream links checked, not assumed unaffected.
3. **Approve:** per `docs/decisions/APPROVAL_GATES.md`'s own rule — *"No gate may be inferred from
   Claude's own recommendation"* — a scope/contract/plan change during coding needs the same
   explicit user confirmation any earlier gate needed. A recommendation may be offered; it is not
   self-approving.
4. **Record:** update the Decision Register (new resolution entry, dated, attributed) and every
   downstream document the impact-check identified — not just the one document that prompted the
   change.
5. **Re-baseline delivery estimate, if the change touches scope or complexity:** `IMPLEMENTATION_
   PLAN.md` §2's effort figures are per-feature-complexity-derived — a scope change (new feature,
   re-scoped `BLOCKED`→`CURRENT`, complexity re-estimate) should trigger a delta calculation using
   the same disclosed methodology, not a silent schedule slip.

Every open item in `PRD_OPEN_ITEMS.md`, `FEATURE_QUESTIONS.md`, and `RAID.md`'s Dependencies section
is a **known, expected future change-control event**, not a surprise. The highest-likelihood ones,
given their position in the dependency graph (`DEPENDENCY_PLAN.md`):
- Employer↔Placement Team mediation workflow (`FEATURE_QUESTIONS.md` #1) — affects `EMP-002`'s
  `Job.status` state machine.
- Employer-approval-before-activation (`FEATURE_QUESTIONS.md` #7) — affects `EMP-001`'s activation
  gate.
- GDPR retention periods (`PRD_OPEN_ITEMS.md` item 15) — affects `SEC-002`'s deletion-hold logic.
- Notification retry policy (`PRD_OPEN_ITEMS.md` item 13) — affects `NOT-001`–`003`'s retry
  mechanism.
- Batch-naming convention, document checklists, commission "joined" event's final real-world
  verification step — each affects one specific, already-identified feature's UI/data completeness,
  not its core mechanism (`DATA_MODEL.md`/`API_CONTRACT.md` already designed the mechanism to accept
  these answers without a structural rebuild).

## 5. What this document does not do

It does not pre-approve any of §4's likely changes — each still goes through §3 when it actually
happens. It does not create a change-approval board or role beyond "the user," consistent with every
other approval gate in this project having exactly one approver.
