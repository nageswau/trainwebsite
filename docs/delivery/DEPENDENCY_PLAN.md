## 1. Why streams matter for this project specifically

`FEATURE_DEPENDENCY_MAP.md`'s four illustrative dependency chains never cross except at the shared
`FND-001`/`FND-002`/`AUTH-001` root — domestic (Student/Trainer/Admin/Payments) and Overseas
(destinations/applications/visa/agent/counselor) share almost no feature-level dependency. This is the
single largest lever available to compress `IMPLEMENTATION_PLAN.md` §2.5's calendar-time estimate
without changing total effort — confirmed structurally, not assumed.

## 2. The four streams

### Stream A — Foundation (blocks B/C/D, cannot itself be parallelized internally)
`FND-001` → `FND-002` → `AUTH-001` → `AUTH-002`; `OPS-001` → `OPS-002` (can run alongside the
FND/AUTH chain, not blocked by it — both just need to land before any other stream starts against a
shared environment).

**Definition of ready:** reference-implementation source accessible; DigitalOcean account exists.
**Definition of done:** a protected route correctly enforces division+role deny-by-default; the app
is deployed and migrated on DigitalOcean.

### Stream B — Domestic core (depends only on Stream A)
`PUB-*` → `ADM-001`–`003` → `TRN-001`–`002` → `STU-001` → (`STU-009`, `STU-010`‖`PAY-001`) →
`TRN-003`/`STU-003` → `TRN-005`/`STU-004`/`TRN-007` → `TRN-008` → `STU-002` → `ADM-005` → Wave-2/3
domestic depth (`STU-005`–`008`,`011`, `TRN-004`,`006`,`009`, `ADM-004`,`006`–`008`,`014`, `RPT-001`).

**Definition of ready:** Stream A done; `DATA_MODEL.md` §3–5 approved ✓; `API_CONTRACT.md` §3–5
approved ✓.
**Definition of done:** a Visitor can become an enrolled, paying, learning Student, graded by a
Trainer, visible to an Admin — the full domestic loop, per `UAT-001`/`UAT-002`.

### Stream C — Overseas core (depends only on Stream A, not on Stream B)
`OVS-001` → `OVS-002` → `OVS-003` → (`OVS-004`‖`OVS-005`) → `VISA-001` → `VISA-003` → `VISA-002`;
`CNS-001` needed before `OVS-003` (Counselor is the actor advancing eligibility); `OVS-006`/`007`

Agent sub-stream (depends on Overseas core reaching `OVS-002`/`OVS-004`, not on the full chain):
`AGT-001` → `AGT-002` → `AGT-003` → `AGT-004`.

**Definition of ready:** Stream A done; `DATA_MODEL.md` §6 approved ✓ (including the `ADR-012`

**Definition of done:** a Student can discover a destination, apply, be evaluated by a Counselor,
upload/verify documents, track visa status, and (Agent sub-stream) an Agent can register, get
approved, refer, and be paid a commission through the two-gate control — per `SEC-AUDIT-01` and
`AGT-COMM-01`/`AGT-PAYOUT-01` (`TEST_REWRITE_PLAN.md` §4–5).

### Stream D — Employer (depends only on Stream A, fully independent of B and C)
`EMP-001` → `EMP-002` → `EMP-003` → `EMP-004` → `EMP-005`.

**Definition of ready:** Stream A done; `DATA_MODEL.md` §5.1 (`ADR-011` resolution) approved ✓;
`FEATURE_QUESTIONS.md` #1 (Employer↔Placement Team mediation) and #7 (approval-before-activation)

per the contracts, meaning Stream D can technically start without them, but `EMP-002`'s exact
publish-workflow behavior will need rework if answered after the fact. **Recommend resolving both
before Stream D's first sprint**, flagged as a pre-stream risk, not a hard blocker.
**Definition of done:** an Employer can register, post a job, search GDPR-scoped candidate profiles,
shortlist, and schedule interviews — per a new "Employer Journey" UAT case (retargeting `UAT-004`).

### Cross-cutting stream E — Notifications/Payments/Security (feeds B, C, D; not a separate team necessarily)
`NOT-001`–`003`, `PAY-001`, `SEC-001`–`002` — small, mostly-independent features each stream consumes
(e.g. `OVS-004` needs `NOT-001`/`002` to exist). Recommend building these early enough in Wave 1/2
that Streams B/C/D aren't blocked waiting on them, per `FEATURE_DEPENDENCY_MAP.md`'s explicit edges.

## 3. Minimum viable parallel team shape

Given the streams above, `IMPLEMENTATION_PLAN.md` §2.5's "4 engineers" scenario maps naturally to:
1 on Stream A (then rolls onto B or C once done), 1–2 on Stream B, 1 on Stream C, with Stream D and E
work absorbed by whichever engineer is between milestones — **illustrative, not a staffing
requirement**, since actual team composition is unconfirmed (`IMPLEMENTATION_PLAN.md` §2.5).

## 4. Checkpoint discipline between streams

Streams B/C/D do not need to wait for each other's Wave-2/3 completion — only for Stream A and their
own within-stream dependencies. The **wave numbering in `RELEASE_BACKLOG.md` reflects a recommended
build/test/release checkpoint cadence**, not a hard technical blocker between streams — a team could
legitimately have Stream C (Overseas) reach its Wave-3 Agent milestone before Stream D (Employer)
finishes its Wave-2 features, without violating any dependency. Release milestones (`M1`/`M2`/`M3`)
should be read as "everything scheduled up to and including this wave, across all streams, is done
and gated," not "streams complete in this exact order."
