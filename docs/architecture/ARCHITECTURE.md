## 2. Architecture style — CONFIRMED, not preselected here

**Domain-oriented modular monolith.** This is `DEC-ARCH-001`, confirmed by the user directly, with a
documented revision history: an earlier same-session "microservices" confirmation was itself revised
back to modular monolith specifically because this project extends an existing modular-monolith
codebase — rewriting its architecture would be a rebuild, not an extension. This document does not
re-decide this; it designs against it.

**Rationale (inherited from the reference implementation's own architecture record, still valid):**
reduces service-to-service networking, distributed transactions, observability overhead, and
deployment complexity for the current team size, while keeping the two business divisions logically
independent through domain modules, RBAC, a `division` column, and route boundaries — not through
separate deployable services. High-load domains remain extractable behind stable API boundaries
later if metrics justify it (see §11 Portability).

### 3.1 Employer domain (net-new)

No equivalent role, table, or route exists in the base codebase. Requires: an `Employer` role value
alongside the existing `it`-division roles, new tables (company, job posting, shortlist — the base
codebase's existing `Company`/`Job`/`JobApplication`/`Interview`/`JobOffer` models are currently
owned by internal Placement Team/HR Team workflows and would need either extension with an
`employer_id` ownership column or a parallel table set — **this specific data-modeling choice is
Contracts-phase work, `prompts/09`, not decided here**), new API routes, new RBAC rules. Relationship
to the existing Placement Team/HR Team workflow is explicitly undefined
(`FEATURE_QUESTIONS.md` item 1) — this architecture treats Employer as an additive module pending
that answer, not as a replacement for the existing internal-staff flow.

### 3.2 Overseas commission extension

The base codebase's `AgentCommission` model and its manual-creation/claim flow are reused as-is for
data shape (admin-discretionary `amount`, `currency`, `status` lifecycle: `eligible`/`estimated` →
`claimed` → `paid`). Two behaviors are added on top, not replacing existing code:
1. An automatic trigger that creates/marks a commission eligible when `OverseasApplication.status`
   reaches a "joined" terminal state — **that specific status value does not yet exist in the base
   codebase's own status vocabulary** (only `profile_evaluation → university_review` was observed
   in its seed data). Defining it is Contracts-phase work (`FEATURE_QUESTIONS.md` item 4).
2. A new `claimed → paid` approval endpoint requiring Overseas Admin action — genuinely new API
   surface (`FEATURE_QUESTIONS.md` item 5).

## 5. Storage, cache, and background jobs

Carries over from the base codebase, unchanged in shape (PostgreSQL primary store, Redis for
caching/session-adjacent data, Celery for background/async jobs — notification delivery, report
generation, slow provider calls). What changes is only the *hosting* of these three (AWS RDS/
ElastiCache → DigitalOcean equivalents), covered in `DEPLOYMENT.md`, not the architectural role each
plays.

## 6. Auth / session approach

Carries over from the base codebase's security baseline, unchanged — this was never in conflict
with any confirmed decision: bcrypt password hashing, short-lived access JWT, refresh JWT in a
separate `HttpOnly` cookie, `Secure` cookie flag in production, `SameSite=Lax`, deny-by-default on
every protected route, and — critically — **backend-enforced role/division checks that never trust
the frontend** (`FND-002`, `NFR-SEC-001`). Google OAuth as an additional login method
(`AUTH-003`) remains `BLOCKED` — `PROPOSED`, unconfirmed — and is not designed here.

## 7. File delivery

Carries over in shape: object storage for documents/media (résumés, Overseas application documents,
course resources, certificates), private-by-default with least-privilege access — Overseas
application documents specifically may include passports and financial evidence, requiring the same
least-privilege posture the base codebase's own security baseline already specifies. Provider is
DigitalOcean Spaces instead of S3 (see `DEPLOYMENT.md`) — the *access-control model* does not change
with the provider swap.
