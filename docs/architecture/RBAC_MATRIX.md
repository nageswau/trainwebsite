**`DEC-ROLE-004` (2026-09-14) — Agent on-behalf-of a referred student, NOT YET BUILT:** the
approved Agent row above is read-only (view roster/commissions, claim). Since an Agent-referred
student is never issued a login, the Agent must also **create** the referral (`AgentStudent`) and
perform the write actions `OVS-002`/`004`/`005` currently reserve for `Self (Student)` — submit an
application, track its status, upload documents — on that student's behalf. **This is new grant
scope, not covered by any existing row in this matrix.** §3's own "Support-staff impersonation: None
— not designed... requires its own Decision ID and audit design" is exactly what this is: an
act-on-behalf-of capability. `DEC-ROLE-004` is that Decision ID; the audit design (which specific
endpoints, and how every such write is attributed to the acting Agent rather than looking like the
student's own action) has **not** been designed yet — no RBAC grant, endpoint, or schema change has
been made. See `DATA_MODEL.md` §6.2/§6.8 and `PRD_OPEN_ITEMS.md` item 68.

**Explicit deny — two-gate commission separation (`NFR-SEC-002`):** the `overseas_admin` identity
that creates or adjusts a commission's `amount` should not be the sole actor also approving its
payout where system enforcement can distinguish the two actions (i.e. for admin-manual creation,
require a second Overseas Admin identity to approve payout; for system-triggered accrual, any
Overseas Admin may approve since no single admin created it). This is the concrete enforcement of
the "cannot be bypassed" requirement in `NFR-SEC-002` — implemented as a same-actor check, not
merely a documented intent.

`school_principal`/`school_coordinator`/`school_teacher`/`school_parent`'s own-institution deny above,
except scoped to a portfolio (potentially several schools) rather than exactly one.

**Explicit deny — results same-actor restriction (`DEC-ROLE-007`):** the `academic_team` member who
uploaded a result (`uploaded_by_user_id`) may never also be recorded as its `verified_by_user_id` or
`published_by_user_id` — a verify/publish attempt by the uploader themselves is rejected (`SCH-006-
AC04`), same shape as `AGT-004`'s commission-payout same-actor restriction (`NFR-SEC-002`). This
means a school portfolio with only one `academic_team` member assigned can never publish its own
results — an operational consequence of `DEC-ROLE-007`, not a bug; a portfolio needs at least two
`academic_team` members for `SCH-006` to be usable end-to-end.

documentation):** `school_teacher`'s permission checks must be entirely separate from `trainer`'s

entirely separate from `coordinator`'s (`DEC-ROLE-003`, certificate-issuance role). These are
same-spirit names for genuinely different roles — a shared permission check by accident would be a
real privilege-boundary bug, not a naming quibble (`SCH-001-AC05`).

| List / cancel requests | the `school_coordinator` of the school that **filed** them | every other school, including the destination school of a request it did not file (`DEC-SCOPE-022` D5) |
| Approve / reject / view the admin queue and a student's full transfer history | `overseas_admin`, `super_admin` | `school_coordinator` (either school), `school_principal`, `school_teacher`, `school_parent`, the three service-delivery roles, `counselor`: `403` |
| Read a student's approved transfer history | the same own-scope rule as the student (own institution; assigned-only Teacher; linked-only Parent); no reason, no staff IDs | any role outside that scope |

Filers (`school_coordinator`) and approvers (`overseas_admin`, `super_admin`) are disjoint roles, so no user can both file and approve. **Parent scope change:** a `school_parent`'s read scope is their `SchoolParentLink`s alone, not the school on their account (a transferred child lives at another school than the parent's account); an unlinked student now gets a single generic `403` ("This student is not linked to your account") — reduced from two distinct messages to one (`ENH-008` Task 3's reordering of `_load_readable_student`, below). **Consequence for account authority:** a parent moved to the gaining school appears in that school's coordinator's team list and can be activated/deactivated by them (`update_team_account`), and leaves the losing coordinator's. Covered by the `test_enh_005_*.py` files.

**Addendum, 2026-09-22 (`ENH-008`) — cross-school parent linking, same-school invariant removed.** The

## 3. Support / admin audit controls

| Control | Applies to | Requirement |
|---|---|---|
| Privileged-write audit trail | Agent approval/rejection, commission payout approval, GDPR fulfil/reject, Super Admin security-log export, any Admin field-level override (certificate override, cascade-delete confirmation) | Every action writes an `AuditLog` row (actor, timestamp, outcome) in the **same transaction** as the privileged write — a failed audit write fails the underlying action, fail closed (`SEC-001-AC02`, `DATA_MODEL.md` §7.3). |
| School Coordinator writes | Single-record student create/manage, and every bulk-roster-upload batch | Every write is attributable to the acting Coordinator; a bulk batch gets one batch-level `AuditLog` entry (actor, timestamp, accepted/rejected row counts) per `DATA_MODEL.md` §6.13 — extends the privileged-write audit trail rule above to this new external-facing write path (`SCH-001`, `SCH-002`). |
| School/account provisioning | Overseas Admin creating a School + seed Coordinator; Coordinator inviting/creating Principal/Teacher/Parent | Every creation writes an `AuditLog` row (actor, timestamp, created entity, institution). An invite token's issuance and its consumption (accepted/expired) are both logged separately — a consumed invite being reused, or used for a different institution, must be independently detectable from the audit trail, not just blocked in the moment (`SCH-003`). |
| Specialized-role provisioning | Overseas Admin or Super Admin creating an `academic_team`/`career_counselor`/`psychometric_team` account and assigning its school portfolio (`DEC-SCOPE-013`/`014`) | Every creation writes an `AuditLog` row (actor, timestamp, created entity, assigned portfolio) — same discipline as School/account provisioning above, extended to this Admin-console path. A later portfolio change (schools added/removed) is its own audit row too, not a silent update. |
| School service-delivery writes | Academic Team result upload and every `Draft → Verified → Published` transition; Career Counselor session/note/recommendation writes; Psychometric Team assessment/report writes | Every write and every gate transition is its own `AuditLog` row (actor, timestamp, from-status, to-status where applicable) — a result's full history must be reconstructable from the audit trail alone, not just its current state (`SCH-004`, `SCH-005`, `SCH-006`). |
| Cross-division access | `super_admin` only | Every cross-division read/write is itself audit-logged, not just role-gated — a Super Admin's own broad access is the highest-value target for misuse detection. |
| Field-level Admin edits | `ADM-004` directory management | A PATCH request touching a field outside the acting Admin's field-level grant returns 403 on that field (or the whole request, whichever is simpler at implementation time) — never a silent partial-ignore of the unauthorized field. |
| Support-staff impersonation | None — **not designed.** No role in this matrix grants "act as another user" capability. If a future support workflow needs this, it requires its own Decision ID and audit design, not an assumed extension of an existing admin grant. **`DEC-ROLE-004` (2026-09-14) is exactly this Decision ID for the Agent-on-behalf-of-a-referred-student case (§2.8)** — the decision to allow it exists, the audit design does not yet; every such write must be attributable to the acting Agent, never indistinguishable from a self-service student action, before it is built. |
