# Threat Model Outline

Generated by `prompts/08_ARCHITECTURE_AND_ADRS.md`. Outline-level (per the prompt's "threat model
outline" requirement, not a full STRIDE workshop). Grounded in the base codebase's own stated
security baseline (`docs/evidence/REFERENCE_IMPLEMENTATION_FINDINGS.md` §6) plus threats specific
to this project's confirmed extensions. NO CODE — this identifies risk areas for the Contracts phase
(`prompts/09`) to design controls against, it does not implement any control itself.

**Addendum, 2026-09-14** — a "School domain" subsection added under Domain-specific, per
`DEC-SCOPE-011`/`012` and `DEC-ROLE-006`. This closes the gap `SECURITY_CONTROLS.md` §6A flagged when
it was written: School controls previously extended only the cross-cutting IDOR threat because no
School-specific threat entry existed yet. Original content elsewhere is unchanged.

## Cross-cutting (applies to every domain)

| Threat | Mitigation direction (carried from base baseline unless noted) |
|---|---|
| Frontend-only access control bypass | Backend enforces role+division on every route (`FND-002`) — frontend visibility is never the security boundary |
| Cross-division data leakage (an `it`-division user reaching `overseas` data or vice versa) | `division` column + backend checks; only Super Admin is cross-division |
| Session/token theft | Short-lived access JWT, refresh JWT in separate `HttpOnly`/`Secure`/`SameSite=Lax` cookie |
| Credential stuffing / brute force on login | Rate limiting recommended in the base baseline but not yet implemented — **open item for Contracts phase** |
| Privilege escalation via direct object reference (IDOR) | Every resource-scoped feature in `MASTER_FEATURE_CATALOG.md` states explicit RBAC/resource-scope (e.g. "Trainer, own batch only") — these must become actual authorization checks, not just documented intent |

## Domain-specific

### Overseas application / document domain (new-highest sensitivity)
- **Threat:** exposure of passport/financial documents (`OVS-005`) through misconfigured object-storage
  access or an IDOR on document endpoints.
- **Direction:** least-privilege access confirmed in the base baseline; Spaces (or equivalent)
  buckets private by default, signed/expiring URLs for document access, never public buckets.
- **Threat:** a Counselor or University Representative accessing a case not assigned to them.
- **Direction:** already flagged as a required AC in `SCREEN_CATALOG.md` (`SCR-CNS-002`,
  `SCR-UNI-001`) — server-side scoping, not just filtered UI lists.

### Agent commission domain (new fraud surface)
- **Threat:** an Agent or a compromised Overseas Admin account manipulating referral/commission
  records for financial gain (fake referral, premature payout).
- **Direction:** the confirmed two-gate model (`DEC-SCOPE-005` — automatic accrual trigger tied to
  a real application-status event, then a *separate* Overseas Admin approval before payout) exists
  specifically to prevent a single compromised actor from creating and self-approving a payout.
  Both actions must be audit-logged (`SEC-001`) with actor identity, not just outcome.
- **Threat:** the missing trigger-status mapping (`FEATURE_QUESTIONS.md` item 4) gets implemented
  loosely, allowing a status to be set to "joined" without real verification.
- **Direction:** flagged for Contracts-phase design, not resolved here — do not let an easy-to-set
  status field become the actual trigger without a verification step.

### Employer domain (new, external-party access)
- **Threat:** an Employer account viewing more of a Student's profile than GDPR-approved visibility
  permits (`EMP-003`).
- **Direction:** field-level scoping enforced server-side (the API response itself must exclude
  non-visible fields, not just hide them in the UI) — already an explicit AC in
  `FEATURE_ACCEPTANCE_CRITERIA.md`.
- **Threat:** Employer self-registration used to create fraudulent company accounts to harvest
  candidate data.
- **Direction:** employer-approval-before-activation workflow is an open item
  (`PRD_OPEN_ITEMS.md` item 2) — this is a real risk consideration to raise when that gets
  answered, not something to invent a workflow for now.

### Payments
- **Threat:** forged/replayed payment webhooks marking a fee paid without real payment.
- **Direction:** webhook signature verification is explicitly called out as mandatory in both the
  base codebase's own `PRODUCTION_CHECKLIST.md` and this project's `PRD-PAY-001`/`AC` set — must be
  verified before any webhook is trusted (Razorpay is now the sole payment provider — Stripe removed,
  `DEC-PAY-001` re-resolved 2026-09-03).

### Notifications / CRM webhook
- **Threat:** the CRM webhook (Zoho) or notification providers (Twilio, Email, SMS) treated as
  trusted without verifying inbound webhook authenticity where applicable (e.g. delivery-status
  callbacks).
- **Direction:** provider secrets from environment/secrets manager (base baseline); verify any
  inbound callback signatures the same way payment webhooks are verified.

### GDPR / data protection
- **Threat:** a data export/delete request (`SEC-002`) fulfilled incorrectly — either leaking another
  user's data in an export, or deleting data subject to a legal/financial retention hold.
- **Direction:** self-service request scoped strictly to the requesting user's own data; retention
  holds are an explicit open item (`PRD_OPEN_ITEMS.md` item 15) — do not implement deletion logic
  that ignores a retention requirement that hasn't been defined yet; flag rather than guess.

### School domain (minors' data, net-new, added 2026-09-14)
- **Threat:** cross-institution data leakage — a School role (Principal/Coordinator/Teacher/Parent)
  reaching another institution's students/results/service-delivery content, including via a direct
  record ID.
- **Direction:** own-`school_id` server-side scoping for every School-domain query, same pattern as
  the Overseas domain's University Representative scoping above (`RBAC_MATRIX.md` §2.12,
  `SECURITY_CONTROLS.md` §6A).
- **Threat:** a Teacher or Parent reaching a student outside their own narrower scope (assigned
  students only / own child(ren) only) even within their **own** institution.
- **Direction:** narrower-than-institution scoping is a distinct check from the institution check
  itself, not implied by it — both must be independently enforced (`SCH-001-AC03`).
- **Threat:** unauthorized School partner/account provisioning — a role other than `overseas_admin`
  creating a `School`, or a role other than `school_coordinator` creating a Principal/Teacher/Parent
  account, or an account created for an institution other than the acting Coordinator's own.
- **Direction:** the provisioning gate has no self-service anywhere (`DEC-SCOPE-012`); invite tokens
  are single-use and institution-scoped, checked the same way an account-creation IDOR would be
  (`DATA_MODEL.md` §6.15).
- **Threat (added 2026-09-21, `ENH-005`):** a coordinator pulling another school's student, or learning
  which Student IDs exist at other schools — by filing requests for guessed codes and watching whether a
  row appears in their own list, or by comparing responses for a real and an unknown code.
- **Direction:** the move is only ever performed by an admin's approval; the incoming endpoint answers
  every well-formed code identically; a not-yet-approved incoming row is redacted; filing is throttled
  (30/hour/coordinator, counted from the audit rows so it holds across instances) and capped (50 open per
  school); every attempt is audited with a reason token, never the code. **Residual, stated:** a determined
  coordinator can still learn that a code exists, slowly, and is recorded doing so (`DEC-SCOPE-021`).
- **Threat (added 2026-09-21, `ENH-005`):** markup in a student, school or parent name reaching a parent's
  inbox through the notification email (HTML injection under EduSphere's own sender), or hidden
  bidirectional characters in a transfer reason/note misleading an admin.
- **Direction:** the parent notification email escapes everything it interpolates; free text rejects
  control and bidirectional-override characters and is rendered as text only.
- **Threat:** premature disclosure of an unverified academic result — a family or student sees a
  `Draft`/`Verified` mark before it's confirmed accurate.
- **Direction:** the `Draft → Verified → Published` gate exists specifically to prevent this;
  visibility is filtered server-side to `Published` only, never a UI-only hide (`SCH-006-AC02`).
- **Threat:** malicious or malformed bulk-roster upload used for mass unauthorized student-record
  creation or storage abuse.
- **Direction:** server-side validation before any row commits, row-level accept/reject rather than
  all-or-nothing (`SCH-002-AC04`) — same discipline as every other upload path below.
- **Threat (flagged open, not resolved here):** an `academic_team`/`career_counselor`/
  `psychometric_team` member accessing a school-affiliated student's sensitive service-delivery
  content (results, counselling notes, psychometric reports) outside their actual assignment.
- **Direction:** the assignment-scope mechanism itself is undesigned (`RBAC_MATRIX.md` §5,
  `PRD_OPEN_ITEMS.md` item 76) — this threat cannot be fully mitigated until that mechanism exists;
  carried forward as a named, open risk rather than assumed closed.

### File uploads (general)
- **Threat:** malicious file upload (resumes, assignments, documents, resources) used for stored
  XSS, malware distribution, or storage abuse.
- **Direction:** restricted upload types/sizes (base baseline); malware scanning is listed as a
  recommended-but-not-yet-implemented addition in the base codebase's own architecture doc — carried
  forward here as still-recommended, still not implemented.
