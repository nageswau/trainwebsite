## 1. Authentication

| Control | Detail | Threat addressed | Feature |
|---|---|---|---|
| Password hashing | bcrypt, no plaintext/reversible storage anywhere, including logs | Credential compromise | `AUTH-001` |
| Access token | Short-lived JWT (base codebase default expiry, carried over — exact minutes not independently re-confirmed, treated as inherited baseline) | Token theft blast radius | `AUTH-001`, `FND-002` |
| Refresh token | Separate `HttpOnly`, `Secure` (prod), `SameSite=Lax` cookie — never readable by JS | XSS-driven token exfiltration | `AUTH-001` |
| No user enumeration | Login and password-reset-request return identical generic responses regardless of whether the account exists | Account enumeration | `AUTH-001-AC03` |
| No admin-known or default credential | An account an admin provisions (`POST /admin/users`, `/overseas-admin/schools`, `/overseas-admin/school-staff`) is created with a random, discarded password hash; a supplied `password` is rejected (`422`). The user sets their own through a single-use, SHA-256-at-rest, 72-hour emailed link; consumption is atomic; every failure is the same generic `400`. | Shared/default credentials; admin impersonation of a newly provisioned user | `ENH-003`, `DEC-SCOPE-019` |
| Welcome-link revocation | A welcome link is refused for a deactivated account, and any real change of `active` revokes the account's open welcome links, so a link mailed to a mistyped address cannot come back to life on reactivation | Wrong-recipient account takeover | `ENH-003` |
| Set-password link never leaves the browser | The link carries a live token in its query string, so the reset pages are never configured in Google Analytics (`gtag('config')` reports the full URL) and are served with `Referrer-Policy: no-referrer` and `Cache-Control: no-store` | Token leakage to third parties, Referer, caches | `ENH-003` |
| Rate limiting on auth endpoints | **Open item** — `THREAT_MODEL.md` flags this as "recommended in base baseline but not yet implemented." This contract does not invent a specific rate (requests/minute) without a confirmed target; recommends a conservative default (e.g. 5 failed attempts/15 min per account+IP) be applied at implementation time, flagged for explicit sign-off, not silently treated as decided here. | Credential stuffing / brute force | Cross-cutting |
| Welcome-link Re-send throttle | The only throttle that exists today, and it is **not** a general limiter: one Re-send per account per 60 s after the first (`429` + `Retry-After`), serialized on the user row, so an admin session cannot flood one mailbox. Login, forgot-password and reset remain unthrottled — the open item above still stands. | Mail flooding via an authenticated endpoint | `ENH-003` |
| Change-password brute-force limit | `POST /auth/change-password` allows 5 wrong current passwords per user per 15 minutes (`429` + `Retry-After`), keyed on the authenticated user id (never IP) and counted from the `auth.change_password_failed` audit rows, so it needs no table. The check runs before bcrypt, and blocked attempts are not counted, so a lockout cannot extend itself. **Depends on those audit rows not being purged inside the 15-minute window.** Login, forgot-password and reset-password remain unthrottled — the open item above still stands. A successful change revokes the user's unused password-reset links. **Accepted risks (`DEC-SCOPE-021`):** other sessions survive a password change — a stolen refresh cookie stays usable for up to 14 days (`refresh_token_days`; access tokens 60 minutes) because `/auth/refresh` does not consult the password; a holder of a stolen session can lock the victim out of this route for 15 minutes at a time (forgot-password is unaffected); blocked attempts are logged, not audited, so a flood cannot grow `audit_logs`. | Guessing the current password from a hijacked session | `ENH-006` |
| Server-owned profile scope keys | `PATCH /auth/me` refuses (`403`, audited as `profile.update_denied`, logged as a warning without the value, no other field of that request applied) any change to `profile.school_id` or `profile.university_id`; echoing the unchanged value is accepted. Both keys scope access (the School portal; a University Representative's applications) and only an admin route sets them. Add any future authorization-bearing profile key to `SERVER_OWNED_PROFILE_KEYS` (`app/api/auth.py`) | A logged-in user re-pointing their own tenant scope (horizontal privilege escalation) | `ENH-004` |
| Coordinator-only student promotion | `POST /school/students/promotions` is School Coordinator only (`403` for every other role), the school is derived from the caller and every requested student is locked and filtered by it, so a student of another school and an unknown id are indistinguishable (`403`). Denied attempts are audited (`school.student_promotion_denied`) and logged with counts and ids only. The screen also refuses non-coordinators before loading their roster | Cross-school promotion (IDOR); a Parent, Teacher or Principal changing grades | `ENH-004` |
| Google OAuth | **Not designed** — `AUTH-003` is `BLOCKED` (`PRD-AUTH-003` unconfirmed) | — | `AUTH-003` (blocked) |

## 2. Authorization

| Control | Detail | Threat addressed | Feature |
|---|---|---|---|
| Backend-enforced RBAC on every protected route | Per `RBAC_MATRIX.md`; frontend hiding (`AUTH-002`) is never the security boundary | Frontend-only bypass | `FND-002`, `AUTH-002` |
| Division isolation | Every division-scoped query filtered by the authenticated user's division; only `super_admin` crosses | Cross-division data leakage | `FND-002` |
| Resource-scope enforcement at the query layer, not the response layer | A Trainer's batch query is scoped `WHERE trainer_id = :current_user`, not "fetch all, filter in code" — prevents a class of IDOR where a filter is forgotten on one endpoint | IDOR (`THREAT_MODEL.md` cross-cutting) | All resource-scoped features (`RBAC_MATRIX.md` §4) |
| Server-derived identity only | No endpoint accepts a client-supplied `user_id`/`agent_id`/`university_id` as an authorization input — always derived from the verified JWT | IDOR | Cross-cutting |
| Existence masking where appropriate | A Trainer requesting another Trainer's batch gets 403, not 404-with-details, per `RBAC_MATRIX.md` §4 — but 404 (not 403) for a genuinely nonexistent resource, so error codes don't themselves leak scope boundaries inconsistently | IDOR / enumeration | `TRN-002-AC02` |
| School own-institution scoping | Every School-domain query filtered server-side by the acting user's `school_id`, never a client-supplied filter — same class as `UNI-001`/`AGT-002`. `school_teacher` additionally scoped to assigned students only, `school_parent` to own child(ren) only, both narrower than the institution-wide scope (`RBAC_MATRIX.md` §2.12) | Cross-institution data leakage; IDOR | `SCH-001-AC02`/`AC03` |
| School role-name collision guard | `school_teacher`'s permission checks are a distinct role identifier from `trainer`; `school_coordinator`'s are distinct from `coordinator` — never reachable through the other's check, even by accident | Privilege-boundary bug via naming collision | `SCH-001-AC05` |
| School results Published-only visibility | `school_coordinator`/`school_parent`/Teacher queries filtered server-side to `status=published`; a `draft`/`verified` result is never returned, including on direct-ID lookup (`API_CONTRACT.md` §12A masks this as 404) | Premature disclosure of unverified academic data | `SCH-006-AC02` |
| School provisioning gate | No role below `overseas_admin` creates a `School`; no role below `school_coordinator` creates a Principal/Teacher/Parent account; a Coordinator's invite is always scoped to their own `school_id`, never client-supplied | Unauthorized institution/account creation | `SCH-003-AC02`/`AC03` |

## 3. Secrets & credential management

| Control | Detail | Threat addressed | Feature |
|---|---|---|---|
| Secrets manager (DigitalOcean App Platform environment/secrets, per `ADR-004`) | All provider credentials (Zoho, Razorpay, Zoho Meeting, Google Meet, Twilio, DO Spaces keys), DB/Redis credentials, JWT signing key | Credential leakage via source control or logs | `OPS-001`, all integration features |
| No secrets in `.env` committed to version control | Carried over from base codebase's own stated practice | Same | `FND-001` |
| Secrets never logged | Application logs (`ARCHITECTURE.md` §8) must redact/exclude credential values, tokens, and full payment-card-adjacent data | Log-based leakage | Cross-cutting |
| Welcome-link logs and audit rows carry ids and statuses only | Never the raw token, the recipient's address, or a URL: SMTP/webhook error text is stripped of both (webhook errors can echo a URL that embeds a secret; SMTP refusals often echo the address) before it is stored or logged | Log/audit-based leakage | `ENH-003` |
| **Deployment checklist — `ENVIRONMENT`** | The API's `ENVIRONMENT` must be `production` in every deployed environment. The API reads it from `.env` (the code default and `.env.example` are `development`; the compose file's `production` default applies only to the *web* service). Left at `development`, responses carry `development_welcome_token` and — pre-existing, outside `ENH-003` — `POST /auth/forgot-password` returns `development_reset_token` to anonymous callers (account takeover of any user). Also confirm `COOKIE_SECURE=true` and a real `SECRET_KEY` (the code default is `change-me`). | Live credentials in responses; forged sessions | Release checklist |

## 5. File upload security

| Control | Detail | Threat addressed | Feature |
|---|---|---|---|
| Restricted upload types/sizes | Enforced server-side (not just an `accept=` UI hint), per-feature limits (assignment files, resumes, Overseas documents, resources) — clear `field_errors` rejection, never silent drop | Malicious upload, storage abuse | `STU-004`, `STU-011`, `OVS-005`, `TRN-004`, `EMP-002` (resume via public apply) |

Recommend integrating a scanning step (e.g. at the object-storage adapter layer) before Contracts approval is treated as covering this fully, or explicitly accept the gap as a release risk. | Stored malware distribution | `PUB-005`, `OVS-005`, `STU-004` |

## 6A. School domain (minors' data, high sensitivity) — addendum, 2026-09-14

School-affiliated students are plausibly minors (`EVID-014`'s K-12/school context, not independently
re-confirmed beyond that inference) — treated here with the same least-privilege discipline as the
Overseas document domain in §6, extended to cover writes as well as reads.

| Control | Detail | Threat addressed | Feature |
|---|---|---|---|
| Least-privilege student-record access | Coordinator (own institution, write); Principal (own institution, read-only); Teacher (own institution + assigned only, read-only); Parent (own institution + own child(ren) only, read-only) — server-scoped, per `RBAC_MATRIX.md` §2.12 | Unauthorized access to a minor's institutional record | `SCH-001-AC02`/`AC03` |
| Write-access concentration | Only `school_coordinator` writes student records; only `academic_team`/`career_counselor`/`psychometric_team` write their respective service-delivery content — no other role, including Principal, has any create/edit/delete grant | Unauthorized modification of a minor's academic/service-delivery record | `SCH-001-AC04`, `SCH-004-AC04`, `SCH-005-AC04` |
| Results gate before disclosure | A result is never visible to Parent/Student/Teacher until `Published` — protects against a Draft/Verified (potentially incorrect) mark reaching a family before it's confirmed | Premature/incorrect disclosure of a minor's academic standing | `SCH-006-AC02` |
| Service-delivery content scope (Career Guidance, Counselling, Psychometric) | Assigned-student-only for the three specialized roles — **the assignment mechanism itself is undesigned** (`RBAC_MATRIX.md` §5, `PRD_OPEN_ITEMS.md` items 75–76); this control cannot be fully verified as enforced until that mechanism exists, flagged as an open gap rather than assumed closed | Unauthorized access to sensitive counselling/psychometric data about a minor | `SCH-004`, `SCH-005` |
| Cross-institution isolation | No School role ever reads another institution's data, even via a direct record ID; no client-supplied `school_id` filter overrides server-derived scope | Cross-institution data leakage (extends the cross-cutting IDOR threat, `THREAT_MODEL.md` §Cross-cutting) | `SCH-001-AC02`, `RBAC_MATRIX.md` §4 |

## 7. Agent commission fraud surface

|---|---|---|---|

## 10. Audit logging

| Control | Detail | Threat addressed | Feature |
|---|---|---|---|
| Fail-closed audit writes | A privileged action (Agent approval, commission payout, GDPR fulfilment, Super Admin cross-division action, Admin override) is aborted if its `AuditLog` write fails — never proceeds unlogged | Undetected privileged-action abuse | `SEC-001-AC02` |
| Actor + outcome recorded, not just the action | Every audit row has `actor_user_id`, `outcome`, timestamp | Forensics / accountability | `SEC-001` |
| Password-change audit | `auth.change_password` and `auth.change_password_failed` (`outcome=denied`) rows carry ids only — never a password or hash. The failure row is committed before the `400` is raised, so it survives the error and feeds the limiter | Forensics; limiter integrity | `ENH-006` |
| Fail-closed audit writes, School domain | School partner/account creation, invite issuance/consumption, bulk-roster-upload batches, and every result `Draft`→`Verified`→`Published` transition each write their own `AuditLog` row in the same transaction as the underlying write, extending the same fail-closed rule above (`RBAC_MATRIX.md` §3) | Undetected unauthorized provisioning or record tampering in the School domain | `SCH-002`, `SCH-003`, `SCH-006` |
