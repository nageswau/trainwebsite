## Option comparison (recommendation, not a decision)

| Dimension | Option A — DigitalOcean App Platform | Option B — Droplets + DOKS (Kubernetes) | Option C — Plain Droplets (self-managed) |
|---|---|---|---|
| **What it is** | PaaS: push a container/repo, DO handles build/deploy/scaling for web+API tiers | Managed Kubernetes cluster running the same containers | Manually provisioned VMs running Docker Compose (closest to the base codebase's existing local dev setup) |
| **Cost** | Predictable per-app pricing; scales with instance count/size; no cluster-management overhead cost | Cluster overhead (control plane has a cost; node pools sized for peak, not average, unless autoscaling tuned) — generally higher baseline cost than App Platform for this scale | Lowest raw compute cost, but hidden cost in engineering time to manage patching/scaling/failover manually |
| **Scale** | Horizontal autoscaling built in; sufficient for concurrency levels this project can currently justify (see `SCALING.md` — no confirmed RPS target exists to size against precisely) | Highest ceiling — most appropriate if/when domains are later extracted per the portability strategy (`ARCHITECTURE.md` §10) | Lowest ceiling without significant manual ops investment |
| **Maintenance** | Lowest — DO manages the runtime, OS patching, TLS | Moderate-to-high — team owns cluster upgrades, node management, ingress config | Highest — team owns everything: OS patching, process supervision, TLS renewal, zero-downtime deploys |
| **Security** | DO manages the platform attack surface; still need app-level controls (rate limiting, WAF equivalent) per the base security baseline | Same app-level responsibility, plus cluster RBAC/network-policy surface to secure correctly | Same app-level responsibility, plus full OS/network hardening burden on the team |
| **Fit for a modular monolith (2 containers: web, API) + worker + managed DB/cache** | **Good fit** — this topology is exactly what App Platform is designed for; no orchestration complexity needed for 2-3 long-running services | **Overkill for the confirmed architecture** — Kubernetes' value is multi-service orchestration; a modular monolith has one API service, one web service, one worker, which doesn't need a cluster scheduler | Workable, matches the base codebase's own `docker-compose.yml` almost directly, but reintroduces exactly the deployment-complexity cost that `DEC-ARCH-001`'s own stated rationale (§2) was chosen to avoid |

## Recommendation (not a decision — requires explicit confirmation)

**Option A — DigitalOcean App Platform**, with DigitalOcean Managed Databases (PostgreSQL),
DigitalOcean Managed Redis (Valkey-compatible), and DigitalOcean Spaces (S3-compatible object
storage) for the supporting services, plus a DO App Platform "worker" component for Celery.

**Rationale:** Option B's orchestration complexity contradicts the exact reasoning `DEC-ARCH-001`
already gave for rejecting microservices — there is no multi-service workload here that needs
Kubernetes' scheduling model. Option C reintroduces the operational burden a small team would
struggle with, and duplicates App Platform's managed capabilities at higher engineering cost for no
scale benefit at this project's currently-known size. Option A is the only one that matches "modular
monolith, small team, two-tier web+API, no confirmed need for extreme scale" without over- or
under-building.

**This is a recommendation only.** Per this session's explicit instruction not to preselect, no
DigitalOcean service has been provisioned or assumed configured — this requires the same kind of
explicit confirmation every other Decision ID in this project has received.

## Email delivery (`ENH-032`, `DEC-SCOPE-225`)

DigitalOcean blocks outbound SMTP (ports 25/465/587) on the account, so the dev and prod droplets cannot use `EMAIL_TRANSPORT=smtp`. App email goes over HTTPS through the Zoho Mail REST API instead (contract: `INTEGRATION_CONTRACTS.md` §4, ENH-032 update). Owner setup:

1. In `https://api-console.zoho.in`, create a **Server-based** client (separate from the Zoho Meeting client).
2. Generate a refresh token for it with the scopes `ZohoMail.messages.CREATE,ZohoMail.accounts.READ`.
3. Find the mailbox's account id with `GET https://mail.zoho.in/api/accounts` (header `Authorization: Zoho-oauthtoken <access token>`).
4. Confirm `info@edusphere.org.uk` is that mailbox or one of its aliases (Zoho rejects a `fromAddress` that does not belong to the account).
5. In the server `.env` set `EMAIL_TRANSPORT=zoho_api`, `SMTP_FROM_EMAIL=info@edusphere.org.uk`, `ZOHO_MAIL_CLIENT_ID`, `ZOHO_MAIL_CLIENT_SECRET`, `ZOHO_MAIL_REFRESH_TOKEN`, `ZOHO_MAIL_ACCOUNT_ID` and `ZOHO_MAIL_API_BASE=https://mail.zoho.in`. `ZOHO_ACCOUNTS_URL` must be the same data centre (`https://accounts.zoho.in`).
6. Recreate the **api, worker and beat** containers so they read the new `.env` (prod: `docker compose up -d --no-deps api worker beat`).
7. Inside the api container run `python -m app.send_test_email --to <your address>`. Exit 0 = sent, 1 = failed (the reason is printed), 2 = not configured. Check the message arrives from `info@edusphere.org.uk`, note the display name and logo, and reply to confirm the reply goes to `info@` (the live check, `ENH-032` AC8; record the result in the QA evidence).

Notes:
- Over the API there is no Reply-To (replies go to the From address) and the inline logo is omitted.
- `NEEDS_CONFIRMATION`: Zoho Mail's daily sending limit for the mailbox depends on the plan; the owner checks it before large bulk sends (for example a school roster invite). A 429 is a permanent failure and is never retried.
- Switching back is a `.env` change only (`EMAIL_TRANSPORT=smtp`), for example if DigitalOcean lifts the SMTP block.
