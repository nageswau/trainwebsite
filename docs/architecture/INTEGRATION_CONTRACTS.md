## 1. CRM webhook (Zoho)

**Direction:** outbound (EduSphere → Zoho), primary. Inbound acknowledgement is optional/config-
dependent (`API_CONTRACT.md` §10).

- **Provider abstraction:** `CRMWebhookAdapter` interface — `sync_enquiry(enquiry) -> SyncResult`.
  Zoho is the **configured target**, not a hardcoded dependency — the base codebase's generic webhook
  framework is kept per `DEC-SCOPE-001`'s extended resolution. A future second CRM target is a config
  change, not a code fork, provided it implements the same adapter interface.
- **Credentials:** Zoho webhook URL + shared secret (or OAuth token, per Zoho's actual integration
  method — **not yet confirmed which**, `DEC-SCOPE-001` confirmed the target, not the auth
  mechanism) stored in the secrets manager (`SECURITY_CONTROLS.md` §3), never in application code or
  version control.
- **Timeout/retry:** outbound call timeout 10s (reasonable default, no confirmed SLA exists — flagged
  as a technical default, not a business commitment). On failure: retry with exponential backoff, 5
  attempts max, then mark `Enquiry.crm_sync_status='failed'` and stop — **never retry indefinitely**,
  and never block the original `POST /public/enquiries` response on sync completion (`PUB-002-AC02`).
- **Outbox pattern:** the `Enquiry` row is written and committed **before** the webhook fires. The
  webhook call is a background job (Celery, carried over from base infra) reading from the committed
  row — this guarantees the enquiry is never lost even if Zoho is unreachable, satisfying
  `PUB-002-AC02`/`ADM-002-AC02` directly.
- **Failure/compensation:** no compensation needed — the local `Enquiry` record is the source of
  truth regardless of sync outcome; `crm_sync_status='failed'` is surfaced in `ADM-002`'s Admin view
  for manual follow-up/retry, not auto-hidden.
- **Ownership:** Engineering owns the adapter code; the actual Zoho account/credentials are a business-
  operations concern (who holds the Zoho login) — **unresolved, not assumed** (mirrors the base
  codebase's own open item on provider account ownership, `PRODUCT_DECISION_REGISTER.md`
  `DEC-LIVE-001` note).

## 2. Payment gateway (Razorpay only)

- **Provider abstraction:** described here as a `PaymentAdapter` interface, but the actual
  implementation (checked directly, 2026-09-03) is a plain `PaymentService.create_checkout` method
  on `services/payment.py` — no formal adapter class/interface exists in code. Razorpay is the sole
  implementation per `DEC-PAY-001`'s 2026-09-03 re-resolution; the Stripe branch has been removed,
  not merely deprioritized. Whether to introduce a formal adapter interface for a single-provider
  system remains the same open flag this document already raised — not resolved by this feature.
- **Credentials:** Razorpay API key/secret + webhook HMAC secret, in the secrets manager. Test/live
  key separation enforced by environment (`DEC-ENV-001`) — TEST-mode credentials (`rzp_test_...`)
  are the ones present in this environment's `.env` as of 2026-09-03.
- **Timeout/retry:** checkout-session creation is a synchronous user-facing call — 15s timeout, no
  retry on the synchronous path (a failed session creation surfaces immediately to the Student to
  retry manually, not silently retried server-side, since a stale retry could create duplicate
  sessions — this is why `POST /payments/{payment_id}/checkout` requires an `Idempotency-Key`,
  `API_CONTRACT.md` §0.2, implemented 2026-09-03: a repeat with the same key replays the cached
  provider order rather than calling Razorpay again).
- **Webhook verification/replay:** every inbound webhook is signature-verified (Razorpay HMAC)
  **before** any `Payment` row is touched — an unverified or invalid-signature event is logged and
  discarded, never processed (`PAY-001-AC03`, mandatory per the base codebase's own
  `PRODUCTION_CHECKLIST.md`). **Idempotency/replay:** `PaymentWebhookEvent.event_id` is unique,
  keyed on Razorpay's own `x-razorpay-event-id` delivery header (confirmed against Razorpay's
  webhook docs, 2026-09-03 — the dedup id is a header, not a JSON body field) — a webhook delivered
  twice (Razorpay retries on non-2xx) is processed exactly once; a duplicate `event_id` is
  acknowledged (200) without reprocessing. Implemented 2026-09-03; both real-signature-verification
  and real-duplicate-delivery behavior are exercised against the live Razorpay TEST API and the
  real webhook secret, not mocked (`test_pay_001_stu_010_payment_gateway.py`).
- **Failure/compensation:** a failed/unverified webhook never marks a fee paid (`PAY-001-AC03`).
  There is no automatic compensation for a payment that succeeded at the provider but whose webhook
  never arrives — this is a reconciliation gap the base codebase does not appear to close either;
  flagged as an open operational item (a manual reconciliation report against the provider dashboard)
  rather than inventing an automated reconciliation job that was never asked for.
- **Ownership:** Engineering (adapter code), Finance/Admin (reconciliation process, provider account).

## 3. Live-class providers (Zoho Meeting default, Google Meet retained)

- **Provider abstraction:** `MeetingAdapter` interface — `create_session(batch, schedule) ->
  MeetingRef`, `get_join_url(session, user) -> URL`, `get_recording(session) -> RecordingRef?`.
- **Credentials:** per-provider API credentials, secrets manager.
- **Timeout/retry:** session creation at batch-scheduling time — 10s timeout, 2 retries. A failure
  here blocks the schedule action itself (better to fail loudly at scheduling time than silently at
  join time).
- **Known limitation, not a defect:** both providers share the one-session-at-a-time recording
  constraint (`DEC-LIVE-001`). `get_recording` returning `null` for a concurrency-limited session is
  an expected, documented outcome (`STU-003-AC02`, `TRN-004-AC02`), not a failure to handle.
- **Failure/compensation:** none needed — no financial/state consequence to a missing recording.
- **Ownership:** Engineering (adapter), account ownership unresolved (`DEC-LIVE-001` note, same as
  CRM).

## 4. Notifications (Twilio WhatsApp, Email provider — unnamed, SMS provider — unnamed)

- **Provider abstraction:** `NotificationAdapter` interface per channel — `send(recipient, template_
  key, context) -> DeliveryRef`. Email and SMS providers are **not named anywhere in evidence**
  (`PRD_OPEN_ITEMS.md`) — the adapter interface is designed so provider selection is a config swap,
  not a code change, precisely because that choice is still open.
- **Credentials:** Twilio Account SID/Auth Token confirmed as the WhatsApp provider (`DEC-NOT-001`);
  Email/SMS provider credentials are placeholders in the secrets manager until selected.
- **Timeout/retry:** async, queued via Celery (carried over). Retry policy (attempt count, backoff)
  is an **open item** (`PRD_OPEN_ITEMS.md` item 13) — this contract fixes the mechanism (a
  `NotificationLog.status='retrying'` state exists, `DATA_MODEL.md` §7.1) but does not invent a
  specific retry count/backoff schedule.
- **Webhook verification (inbound delivery-status callbacks):** Twilio status-callback signature
  verification required before trusting a delivery-status update (`THREAT_MODEL.md` §Notifications/
  CRM webhook) — same signature-verification discipline as payment webhooks, applied here too, not
  a lesser standard just because no money moves.
- **Failure/compensation:** a failed notification never blocks the underlying business event it
  announces (e.g. an application status change is recorded even if the notification fails to send,
  `OVS-004-AC02`) — notification is best-effort, the business state change is authoritative.
- **Opt-out:** `DEC-NOT-001` confirms WhatsApp/Email/SMS as channels but not opt-out rules — a
  `NotificationPreference` capability is schema-ready (not designed in detail here, since the rules
  themselves are the open item, not the mechanism) but not enforced until confirmed.
- **Ownership:** Engineering (adapters), Marketing/Admin (message template content, once
  `ADM-011` — currently `BLOCKED` — is unblocked).

## 5. Object storage (DigitalOcean Spaces)

- **Provider abstraction:** `ObjectStorageAdapter` — `upload(file, bucket_key) -> ObjectRef`,
  `get_signed_url(object_ref, expiry) -> URL`. S3-compatible API means the base codebase's existing
  S3 adapter code is directly reusable against Spaces (`ARCHITECTURE.md` §7) — this is a
  configuration/endpoint change per `ADR-004`, not a new adapter.
- **Access model:** private-by-default buckets, signed/expiring URLs only for all document/resource/
  certificate/recording access — never a public bucket, especially for Overseas application
  documents (passports, financial evidence, `OVS-005` security note).
- **Timeout/retry:** upload — 30s timeout (larger files), 2 retries on transient network failure.
  Download URL generation is synchronous/local (no network round-trip to the provider needed for
  signing), so no retry logic applies there.
- **Failure/compensation:** a failed upload returns a clear error to the client immediately (no
  silent partial upload) — no server-side compensation needed since no DB row is written until the
  upload itself succeeds.
- **Ownership:** Engineering.

## 6. Cross-cutting integration rules

| Rule | Applies to |
|---|---|
| Every outbound integration call happens through its adapter interface, never a direct provider SDK call scattered through business logic | All providers above |
| Every inbound webhook is signature-verified before any state change | Stripe, Razorpay, Twilio status callbacks, Zoho (if inbound ack is used) |
| Every webhook processor is idempotent on `event_id`/equivalent — safe to receive the same event twice | Stripe, Razorpay, Twilio |
| No integration failure blocks the local write it's attached to (enquiry, notification, recording) unless that write's entire purpose *is* the integration (payment, commission payout approval) | CRM, notifications, meetings |
| No integration credential is committed to version control or logged in plaintext | All |
| Provider account ownership (who holds the login/API key) is a separate open item from adapter design for every "retained" provider inherited from the base codebase | Zoho (CRM + Meeting), Twilio |
