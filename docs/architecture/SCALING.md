# Scaling Strategy

Generated by `prompts/08_ARCHITECTURE_AND_ADRS.md`. Per the prompt's explicit instruction: scaling
is based on **concurrency/RPS, not registered-user counts** — a real methodological correction
against how this project's own evidence has framed the question so far.

## Why "10,000+ users" is the wrong number to design against

`NFR-SCALE-001` in `docs/product/PRD.md` states a 10,000+ registered-user goal, sourced from the
client's own original tech-stack document (EVID-010) — but it is marked `PROPOSED (unconfirmed)`,
never independently re-confirmed, and even if it were confirmed, **registered-user count does not
determine infrastructure load.** A platform with 10,000 registered users where 50 are ever online
at once has a trivially different capacity requirement than one with 1,000 registered users all
attending live classes at 6pm simultaneously. Designing DB connection pools, worker counts, or
instance sizing against the user-count figure would be a real engineering mistake, not just an
imprecise one — this document deliberately does not do that.

## What actually drives load in this system (derived from confirmed features, not invented)

| Load driver | Source | Why it matters more than total users |
|---|---|---|
| Concurrent live-class attendance | `STU-003`/`TRN-003`, capped at 20 students/batch (`DEC-WF-002`) | Video/meeting load is provider-side (Zoho Meeting/Google Meet), but session-join, attendance-marking, and Q&A API calls cluster tightly around scheduled class start times — a small number of scheduled time-slots, not a smooth distribution |
| Concurrent enrolment/slot-booking bursts | `STU-001` | New-batch-open or popular-course-launch moments produce short, sharp booking spikes, not steady load |
| Payment webhook bursts | `PAY-001` | Correlated with the same enrolment bursts above; webhook processing must not become a bottleneck at exactly the moment booking traffic peaks |
| Admin/reporting query load | `ADM-*`, `RPT-001` | Low-concurrency but potentially expensive individual queries (funnel/aggregation reports) — needs query-level attention, not just more web instances |
| Overseas application/document-upload bursts | `OVS-002`/`OVS-005` | Likely correlated with application-deadline periods (seasonal), not evenly distributed across the year |
| Notification fan-out | `NOT-001/002/003` | Naturally async (Celery) — should never block a user-facing request regardless of volume |

## No confirmed RPS/concurrency target exists — this is an open item, not filled in with an invented number

Exactly like `NFR-SCALE-001`, no source states a target requests-per-second or concurrent-session
figure. **This document does not invent one.** What it does instead is specify the scaling
*mechanism* so that whatever the real number turns out to be, the system responds to actual
observed load rather than a static, guessed capacity:

1. **Stateless web/API tiers** (already true of the base codebase's Next.js/FastAPI split) —
   horizontal autoscaling triggers on CPU/request-queue depth, not a fixed instance count.
2. **Database connection pooling** sized to the web/API tier's autoscaled instance count, not to a
   registered-user figure.
3. **Redis caching** for reference/catalogue data (courses, countries, universities — high-read,
   low-write) to keep read load off PostgreSQL during traffic spikes.
4. **Celery worker scaling** decoupled from web/API scaling — notification fan-out and report
   generation should never compete with user-facing request capacity.
5. **Pagination everywhere** on admin/reporting lists (already a stated requirement across the
   Feature Catalogue's `ADM-*` features) — prevents a single expensive query from degrading the
   whole tier under load.

## What must happen before real capacity numbers can be set

- A confirmed concurrency/RPS target (or a proxy for it — e.g. "expected simultaneous live
  classes at peak," "expected enrolment-burst size") from the client, not derived from the
  unconfirmed 10,000-user figure.
- Basic observability (`ARCHITECTURE.md` §8, itself not yet confirmed) in place before launch, so
  actual load patterns — not guesses — inform the first real scaling adjustment.

## What this document does NOT do

- It does not size DigitalOcean instance tiers (`DEPLOYMENT.md` — blocked on the same missing
  target).
- It does not treat `NFR-SCALE-001`'s 10,000-user figure as confirmed, even as a planning
  assumption — using it anyway despite it being marked `PROPOSED` would be exactly the kind of
  silent-upgrade-to-confirmed this project has avoided everywhere else.
