## 1. Identity & RBAC domain

### 1.1 `User`
**Purpose:** single authentication identity. **Ownership:** self. **Carries over** from base, with
one structural extension (see below).

- **Constraints:** unique `email`; `password_hash` (bcrypt, never plaintext); `is_active` boolean
  (supports Agent's pending-approval gate, §1.3).
- **Resolves `FEATURE_QUESTIONS.md` #3 (division-pinned identity vs. "same Student identity"):** the
  base codebase pins one `division`+`role` directly on `User`. `DEC-ROLE-001` confirmed a Student and
  an Overseas applicant are **the same identity, extended** — one login must be able to hold both
  `it_student` and `overseas_student` standing. Resolution: **separate identity from
  role-assignment.** `User` no longer carries `division`/`role` directly; a new `UserRoleAssignment`
  join entity (division, role, `assigned_at`, `is_active`) carries one-or-more rows per `User`. Every
  other role (Trainer, Admin, Counselor, Agent, Employer, etc.) gets exactly one active assignment in
  practice — nothing about their behavior changes. Only Student can hold two (`it_student` +
  `overseas_student`) simultaneously. This is additive schema restructuring, not new business scope.
- **Lifecycle:** `active` → `deactivated` (soft; GDPR delete is a separate hard-delete path, §7).
- **Indexes:** unique index on `email` (login lookup, every request). Index on
  `UserRoleAssignment(user_id, division)` (every authorization check, `FND-002`).
- **Audit/retention:** GDPR-scoped (`SEC-002`); export/delete per §7. Password hash never included in
  any export.
- **Feature IDs:** `FND-002`, `AUTH-001`, `AUTH-002`, all role-scoped features.

### 1.2 `UserRoleAssignment` *(net-new, per §1.1 resolution)*
- **Fields:** `user_id` (FK `User`), `division` (`it`/`overseas`/`global`), `role` (one of the 13 role
  values in `docs/product/ROLE_ACTION_MATRIX.md`), `is_active`, `assigned_at`, `assigned_by_user_id`
  (nullable — self-registration vs. admin-created).
- **Constraints:** unique on (`user_id`, `division`, `role`) — no duplicate assignment. A `User` with
  zero active assignments cannot authenticate into any protected route.
- **Lifecycle:** `active` ↔ `inactive` (Admin can deactivate one role without deactivating the whole
  `User` — e.g. an Agent rejected at approval, §1.3, never gets an active assignment at all).
- **Feature IDs:** `FND-002`, `AUTH-001`.

### 1.3 Agent approval gate (fields on `UserRoleAssignment` for `role='agent'`)
- **Fields:** `approval_status` (`pending`/`approved`/`rejected`), `approved_by_user_id` (nullable,
  FK `User`, must resolve to an Overseas Admin assignment), `approved_at`, `rejection_reason`
  (nullable).
- **Constraints:** an `agent` assignment with `approval_status != 'approved'` must not authorize any
  Agent-scoped action (`AGT-002`–`004`) — enforced at the RBAC layer (`RBAC_MATRIX.md`), not just
  hidden in UI.
- **Lifecycle:** `pending` → `approved` | `rejected`. No further transition once `rejected` (a
  rejected applicant must submit a new registration, not be silently re-approved).
- **Audit:** every transition writes an `AuditLog` row (`SEC-001`).
- **Feature IDs:** `AGT-001`.

### 1.4 `PasswordResetToken` (`password_reset_tokens`) — first-time set-password links, `ENH-003`
- **Fields:** `user_id` (FK `User`, indexed), `token_hash` (SHA-256 hex of the raw token, unique — the raw
  token is never stored), `expires_at`, `used_at` (nullable), `purpose` (`reset` \| `welcome`, NOT NULL,
  default `reset`), `superseded_at` (nullable), plus the usual `created_at`/`updated_at`.
- **Purposes:** `reset` — forgot-password, 30-minute expiry. `welcome` — the first-time set-password link
  for an admin-provisioned account (`DEC-SCOPE-019`), 72-hour expiry; consuming it also sets
  `User.email_verified`.
- **Lifecycle:** a token is consumed atomically (`used_at` set only if unused, unsuperseded and unexpired).
  A Re-send, or any real change of the account's `active` flag, sets `superseded_at` on the account's open
  welcome tokens. An account's setup state is derived from its **latest** welcome token (never stored on
  `User`): used, or a later token used ⇒ password set; otherwise `pending_setup` (unexpired) or
  `link_expired` (expired, or revoked with nothing newer).
- **Migration:** `0032_welcome_token_purpose` — additive; existing rows read `purpose='reset'`.
- **Account credential:** an admin-provisioned `User.password_hash` is the hash of a discarded random
  secret, never a constant and never a value any admin chose or saw.
- **Audit:** `user.welcome_link_issue`, `user.welcome_link_delivery`, `auth.welcome_password_set`,
  `auth.password_reset` (`SEC-001`); metadata never holds the raw token, an address, or a URL.
- **Feature IDs:** `ENH-003`.

## 2. Public content / CMS domain

### 2.1 `Page`, `BlogPost`, `NewsArticle`, `GalleryItem`
**Carries over** (base CMS). **Ownership:** Admin/Super Admin (publish), public (read).
- **Lifecycle:** `draft` → `published` → `archived`. Unpublished content is never returned by any
  public-facing endpoint (`PUB-001-AC02`, `PUB-005-AC02` — empty state, not a leaked draft).
- **Indexes:** index on (`status`, `published_at`) for public listing queries.
- **Feature IDs:** `PUB-001`, `PUB-005`.

### 2.2 `CareerPath`, `RealProject`, `SuccessStory`, `BusinessService`
**Correction (`prompts/13`, `PUB-001` build, 2026-09-01):** this section originally said all four
"carry over." Building `PUB-001` found only `Testimonial` (mapping to Success Stories) actually
existed in the base codebase — `CareerPath` and `RealProject` had no equivalent and are **net-new**
tables (list+detail collections, per `PRD-PUB-004`/`PRD-PUB-005`'s explicit "and detail" requirement,
which a single flat page couldn't satisfy); `BusinessService` needed no new table at all — it reuses
the existing generic `ContentPage` model (single page per division/slug, `PRD-PUB-007` has no
"+detail" requirement). Same publish lifecycle as §2.1 for all.
- **Feature IDs:** `PUB-001`.

### 2.3 `Enquiry`
**Carries over**, ownership extended for the CRM webhook. **Ownership:** submitter (public, no
account required) writes; IT Admin reads/routes.
- **Fields:** contact fields, message, source page, `crm_sync_status` (`pending`/`synced`/`failed`),
  `crm_sync_attempts`, `crm_last_error` (nullable).
- **Constraint:** `crm_sync_status` is informational only — an Enquiry is fully valid and
  Admin-actionable regardless of sync outcome (`PUB-002-AC02`, `ADM-002-AC02`); sync failure never
  blocks the local write. See `INTEGRATION_CONTRACTS.md` §2 for the outbox pattern.
- **Retention:** personal data — GDPR-scoped (`DEC-PRIV-001`); export/delete per §7.
- **Feature IDs:** `PUB-002`, `ADM-002`.

### 2.4 `Webinar`, `WebinarRegistration`
**Correction (`prompts/13`, `PUB-004` build, 2026-09-02):** this section originally said both tables
"carried over," the same assumption already corrected once for `PUB-001`'s `CareerPath`/`RealProject`
(§2.2). Building `PUB-004` found no `Webinar` table anywhere in the codebase — the existing `Event`
model already covers this content (division-aware, and the seed data's one IT-division event has
`event_type="Webinar"` literally), so it's reused as-is for listing, no schema change. A
`WebinarRegistration` table genuinely did not exist: `Event.registration_url` only ever held an
external link, so there was no in-app "register" capture for *any* event before this feature —
**net-new** (alembic `0009_webinar_registrations`).
- **Fields (`WebinarRegistration`):** `event_id` (FK → `events.id`), `full_name`, `email`, `phone`
  (nullable).
- **Constraint:** capacity/waitlist rule is an **open item** (`PUB-004-AC02`) — no capacity field
  exists; do not silently enforce an invented cap. A *past* event does reject new registrations
  (409) — that's ordinary temporal correctness (`starts_at` has elapsed), not a capacity rule, and
  is enforced server-side per `PUB-004-AC02`/`SCR-PUB-016`.
- **Feature IDs:** `PUB-004`.

## 3. IT domain — Programs, Batches, Enrolment

### 3.1 `Program`
**Carries over.** **Ownership:** IT Admin.
- **Feature IDs:** `PUB-003`, `ADM-001`.

### 3.2 `Batch`
**Carries over.** **Ownership:** IT Admin (create), Trainer (own batch, read/operate).
- **Fields:** `program_id`, `trainer_id`, `capacity` (≤ 20, `DEC-WF-002`), `slot_start_time`,
  `slot_days`, `status` (`scheduled`/`in_progress`/`completed`/`cancelled`), `naming_code`
  (open item — no confirmed convention beyond the "PY"-style example; do not invent the full
  scheme, store as free text pending `DEC-WF-002`'s still-open batch-naming answer).
- **Constraint:** `capacity <= 20`, enforced at write time (`ADM-003-AC02`).
- **Indexes:** index on `trainer_id` (every `TRN-001` "My Batches" query).
- **Feature IDs:** `ADM-003`, `TRN-001`, `TRN-002`.

### 3.3 `Enrollment`
**Carries over.** **Ownership:** Student (self).
- **Fields:** `student_user_id`, `batch_id`, `status`
  (`pending_payment`/`active`/`completed`/`withdrawn`), `locked_at` (set on booking — once set, the
  `batch_id` is immutable for the enrolment's duration, `DEC-WF-002`), `enrolment_reference` (the
  "unique/enrolment ID" the meeting asked to surface in UI — visibility itself is still an open item
  per `DEC-WF-002`; the field exists in the data model regardless of whether it's UI-exposed yet).
- **Constraints:** a booking request that would exceed `Batch.capacity` is rejected
  (`STU-001-AC02`); once `locked_at` is set, `batch_id` cannot change.
- **Indexes:** index on `student_user_id` (dashboard aggregation, `STU-002`); index on `batch_id`
  (roster queries, `TRN-002`); composite index on (`batch_id`, `status`) for live capacity counts.
- **Audit:** enrolment approval (`ADM-005`) writes actor/timestamp.
- **Feature IDs:** `STU-001`, `STU-002`, `TRN-002`, `ADM-005`.

### 3.4 `Agreement`, `ConsentRecord`
**Carries over/extended.** **Ownership:** Student (self, accept), IT Admin (author agreement text).
- **Fields (`ConsentRecord`):** `user_id`, `agreement_id` (or `consent_type` for non-enrolment
  consents, e.g. Overseas application, Employer registration), `accepted_at`, `ip_address` (evidence
  of consent, not identity tracking), `version` (which agreement text version was accepted).
- **Constraint:** `Enrollment.status` cannot reach `active` without a matching `ConsentRecord`
  (`STU-009-AC02`).
- **Retention:** consent records are retained for the legal-evidence lifetime of the agreement, not
  deleted on a GDPR request that would otherwise remove the user's data (`DEC-PRIV-001` retention
  detail is still open — this is flagged, not resolved, per §7).
- **Feature IDs:** `STU-009`, `SEC-002`.

## 4. Learning domain — Attendance, Assignments, Assessments, Resources

### 4.1 `Attendance`, `AttendanceCorrection`
**Carries over.** **Ownership:** Trainer (write, own batch), Student (read, self).
- **Fields:** `enrollment_id`, `session_date`, `status` (`present`/`absent`/`not_yet_marked` — the
  absence of a row for a session is the "not yet marked" state itself, per `STU-006-AC02`; no
  default-to-absent row is ever auto-created).
- **Indexes:** composite index on (`enrollment_id`, `session_date`).
- **Feature IDs:** `TRN-008`, `STU-006`.

### 4.2 `Assignment`, `Submission`
**Carries over.** **Ownership:** Trainer (author), Student (submit, self).
- **Fields (`Submission`):** `assignment_id`, `student_user_id`, `submitted_at`, `is_late` (computed
  against `Assignment.due_at`, never silently accepted as on-time per `STU-004-AC03`), `file_ref`,
  `score`, `feedback`, `graded_at`, `graded_by_user_id`.
- **Constraint:** editing `Assignment` after `Submission` rows exist does not retroactively alter
  those submissions (`TRN-005-AC02`) — `Assignment` edits are versioned/timestamped, not destructive.
- **Re-grading:** a new grade on the same `Submission` overwrites `score`/`feedback` but the prior
  value is retained in an audit trail (`TRN-007-AC02`) — a `SubmissionGradeHistory` row per grading
  event, not a duplicate `Submission`.
- **Feature IDs:** `TRN-005`, `STU-004`, `TRN-007`.

### 4.3 `Assessment`, `AssessmentQuestion`, `AssessmentAttempt`, `AssessmentAnswer`
**Carries over.** **Ownership:** Trainer (author), Student (attempt, self).
- **Lifecycle (`Assessment`):** `draft` → `scheduled` (visible to Students at/after schedule time) —
  a `draft` Assessment is never returned by any Student-facing endpoint (`TRN-006-AC02`).
- **Feature IDs:** `TRN-006`.

### 4.4 `LearningResource`, `Recording`
**Carries over.** **Ownership:** Trainer (upload, own batch), Student (read, enrolled batch only).
- **Fields (`Recording`):** `batch_id`, `session_date`, `provider` (`zoho_meeting`/`google_meet`),
  `external_recording_ref` (nullable — absent when the concurrent-recording limitation applied,
  `STU-003-AC02`/`TRN-004-AC02`; absence is a normal state, not an error).
- **Feature IDs:** `TRN-004`, `STU-003`.

### 4.5 `SupportTicket`, `TicketMessage`
**Correction (`prompts/13`, `STU-005` build, 2026-09-02):** `TicketMessage` never existed and isn't
built — `STU-005`'s confirmed scope ("Trainer/Admin resolves it") needs a status + a single
resolution note, not a full conversation thread; adding one would be unrequested scope. The
`SupportTicket.assigned_to_user_id` field this section already specified also didn't exist on the
inherited table — added via alembic `0010`, along with `resolution_note` (nullable Text), matching
the "reviewer notes" convention already used elsewhere (attendance-correction review, document
verification). **Ownership:** Student (self, raise), Trainer/Admin (division-scoped, resolve).
- **Fields:** `assigned_to_user_id` (nullable — an unassigned ticket stays visible and open, never
  hidden, `STU-005-AC02`; server-set only, auto-claimed to the first staff member who acts on the
  ticket — never a client-supplied assignee), `resolution_note` (nullable).
- **Feature IDs:** `STU-005`.

### 4.6 `CourseFeedback`
**Carries over.** **Ownership:** Student (self).
- **Constraint:** insertable only where a matching `Enrollment` exists for the (student, batch/
  trainer) pair (`STU-008-AC03`).
- **Feature IDs:** `STU-008`.

### 4.7 `Certificate`
**Carries over.** **Ownership:** IT Admin (issue), Student (read, self).
- **Fields:** `student_user_id`, `enrollment_id`, `issued_by` (`system`/`admin`), `issued_by_user_id`
  (nullable for system-issued), `override_reason` (nullable — required when issued before completion
  criteria are met, `ADM-006-AC02`).
- **Feature IDs:** `STU-007`, `ADM-006`.

### 4.8 `QuestionThread`, `QuestionReply`
**Carries over.** **Ownership:** Student (raise), Trainer (own batch, reply).
- **Constraint:** only the Trainer assigned to the thread's batch may reply (`TRN-009-AC02`); replies

- **Feature IDs:** `TRN-009`.

## 5. Placement / Corporate hiring domain (internal-staff + net-new Employer)

### 5.1 `Company`, `Job`, `JobApplication`, `Interview`, `JobOffer`, `PlacementProfile`
**Carries over**, ownership model **extended** — this is the `ADR-011` resolution.

**Resolution (Contracts-phase technical design, per Architecture §3.1):** extend the existing tables
with a nullable `employer_user_id` (FK `User`, role `employer`) rather than create a parallel table
set. Rationale: `FEATURE_QUESTIONS.md` #1 raises an open *workflow* question (does Placement Team
mediate an Employer-posted job, or does Employer post directly) — a parallel table set would force a
premature answer (it implies "direct, ungated" by construction), while a single table with an
ownership column supports both: `Job.status` gets a `pending_review` value that a mediated workflow
can use and a direct workflow can skip. **This does not answer the workflow question** — it is
recorded as open below and in `RBAC_MATRIX.md` §5 — it only avoids a schema fork that would make one
answer harder to reach later.

- **`Company`:** `owner_type` (`internal` — Placement/HR-team-managed, matching the base codebase's
  existing rows — or `employer_self_service`), `employer_user_id` (nullable, set only when
  `owner_type='employer_self_service'`).
- **`Job`:** `company_id`, `posted_by_user_id`, `status`
  (`draft`/`pending_review`/`published`/`closed`), `closes_at`. **Constraint:** a `Job` past
  `closes_at` is never returned to Students as open, even without an explicit `closed` transition
  (`EMP-002-AC02`) — this is a query-time filter (`status='published' AND closes_at > now()`), not a
  scheduled job that must fire correctly.
- **`JobApplication`:** unchanged shape — both the existing public apply/track-by-code flow (no
  account) and the new Employer-facing candidate search (`EMP-003`, which reads `PlacementProfile`,
  not `JobApplication` directly) coexist without conflict.
- **`Interview`:** `scheduled_by_user_id` (Placement Team or Employer, per `Job.posted_by_user_id`'s
  chain). **Constraint:** overlapping-time conflicts for the same candidate are flagged, not silently
  double-booked (`EMP-004-AC02`) — a uniqueness/overlap check on (`candidate_user_id`,
  `scheduled_at`) at write time.
- **`JobOffer`:** unchanged. Cancelled `Interview` rows are retained (`status='cancelled'`), never
  hard-deleted (`EMP-005-AC02`).
- **Indexes:** index on `Job(status, closes_at)` (every public listing + `EMP-002` query); index on
  `Interview(candidate_user_id, scheduled_at)` (conflict check).
- **Feature IDs:** `ADM-007`, `ADM-008`, `EMP-001`–`005`.

### 5.2 `EmployerProfile` *(net-new)*
- **Fields:** `user_id`, `company_id`, `registration_status`
  (`pending`/`approved`/`rejected` — **only if** the still-open employer-approval-before-activation
  question, `FEATURE_QUESTIONS.md` #7, is confirmed as required; until then this column exists but
  is unenforced/nullable, mirroring the `Webinar` capacity pattern in §2.4 — do not silently gate
  Employer activation on an unconfirmed workflow).
- **Feature IDs:** `EMP-001`.

## 6. Overseas domain — Destinations, Applications, Agents, Commission

### 6.1 `Country`, `University`, `OverseasCourse`, `Scholarship`, `ScholarshipApplication`
**Carries over.** **Ownership:** Admin/backend team (`DEC-DATA-002` — manual maintenance, no external
provider integration).
- **Constraint:** a record with incomplete admin-entered fields (e.g. missing tuition range) renders
  only the fields present — never a fabricated placeholder (`OVS-001-AC02`).
- **Feature IDs:** `OVS-001`, `OVS-006`.

### 6.2 `OverseasApplication`, `ApplicationStatusHistory`
**Carries over**, status vocabulary **extended** — this is part of the `ADR-012` resolution (§6.3
covers the commission-specific piece).

- **Fields:** `student_user_id`, `country_id`/`university_id`/`course_id`, `agent_id` (nullable, FK
  `UserRoleAssignment` for `role='agent'`), `status` (free-text in the base codebase; **this contract
  fixes it to an enumerated set**, derived directly from `DEC-WF-001`'s confirmed base sequence, not
  invented): `enquiry` → `eligibility_evaluation` → `university_selection` → `offer` →
  `visa_documentation` → `status_tracking` → `enrolled`. **Exception-path values (rejected, waitlisted,
  deferred) are explicitly NOT added** — `DEC-WF-001` leaves these open; adding enum values for them
  now would be inventing business rules the user never confirmed. Until confirmed, an application
  that would need one of these outcomes has no valid status transition — this is a deliberate gap,
  carried into `docs/product/PRD_OPEN_ITEMS.md`, not silently patched with a guessed value.
- **Constraint:** submitting interest twice for the same (student, university, course) does not
  create a duplicate row (`OVS-002-AC02`) — unique constraint on (`student_user_id`, `university_id`,
  `course_id`) where `status != 'withdrawn'`.
- **`ApplicationStatusHistory`:** `from_status`, `to_status`, `next_action`, `notes`, `changed_by_id`
  — already present in the base codebase; carried over unchanged as the audit trail satisfying
  `NFR-AUDIT-001` for this domain.
- **Indexes:** index on `student_user_id` (Student's own tracking view); index on `agent_id` (Agent's
  referral roster, `AGT-002`, must never leak another agent's rows); index on `status` (Counselor
  caseload queries, `CNS-001`).
- **Feature IDs:** `OVS-002`, `OVS-003`, `OVS-004`, `CNS-001`, `AGT-002`.
- **`student_user_id` no longer universally means "a self-authenticating Student" — flagged
  2026-09-14, `DEC-ROLE-004` (`CONFIRMED_CURRENT`):** an Agent-referred applicant is never issued a
  login; the Agent creates and manages their record instead. `OVS-002` (submit), `OVS-004` (status
  tracking), and `OVS-005` (document upload) are all `RBAC/resource-scope: Self (Student)` today —
  built and tested only for a self-authenticating applicant. **Open, NOT resolved by this note:**
  whether an agent-referred applicant still gets a real `User` row with `student_user_id` pointing
  to it (created by the Agent, never issued credentials — the base FK/unique-constraint/index design
  above keeps working unchanged), or whether the schema instead needs a nullable `student_user_id`
  with the applicant's identity fields carried on `AgentStudent`/`OverseasApplication` directly. This
  is a genuine architecture choice, not a documentation fix — see `PRODUCT_DECISION_REGISTER.md`
  `DEC-ROLE-004`'s "implementation reconciliation" note and `PRD_OPEN_ITEMS.md` item 68. No schema
  change has been made; this note only records that the previously-safe assumption no longer holds
  universally.

### 6.3 Commission trigger mapping — `ADR-012` resolution
**Resolution:** the automatic commission-accrual trigger (`AGT-003`, `DEC-SCOPE-005`) fires when an
`ApplicationStatusHistory` row is written with `to_status='enrolled'` **for an application that has
an assigned `agent_id`**. `'enrolled'` is not an invented value — it is the literal terminal stage
name `DEC-WF-001` already confirmed ("...→ Enrolment"). This satisfies `FEATURE_QUESTIONS.md` #4
without introducing a new business fact: the trigger condition is "the application reached the stage
the user already named," verified through the existing audit-trail write (not a raw status-field
edit, which could be set without real verification — `THREAT_MODEL.md`'s flagged fraud surface).
**Still open, not resolved by this mapping:** whether "joined the college" (the user's exact trigger
wording in `DEC-SCOPE-005`) is fully synonymous with the `enrolled` status reaching that value, or
whether a distinct downstream confirmation (e.g. a University Representative or Counselor action)
should gate it further — carried forward as an open item for BRD/PRD follow-up, not decided here.

### 6.4 `StudentDocument`
**Carries over.** **Ownership:** Student (upload, self), Counselor (verify).
- **Fields:** `verification_status` (`pending`/`verified`/`rejected`), `reviewer_notes`,
  `verified_by_id`, `checklist_item_key` (references the country/university/course-specific
  checklist — the checklist *content* itself is `DEC-DATA-001`'s still-open item; this field only
  stores which checklist slot a document was uploaded against, whatever that turns out to be).
- **Security:** may contain passports/financial evidence — private-by-default storage, signed/

## 7. Notifications, Payments, GDPR, Audit (cross-cutting)

### 7.1 `NotificationLog`
**Carries over.** **Ownership:** system (write), recipient (implicit).
- **Fields:** `recipient_user_id`, `channel` (`email`/`whatsapp`/`sms`), `template_key`, `status`
  (`queued`/`sent`/`failed`/`retrying`), `attempt_count`, `last_error`.
- **Constraint:** a failed send is retried per policy — **policy itself is open**
  (`PRD_OPEN_ITEMS.md` item 13); this contract fixes only the *mechanism* (a retry-eligible state
  exists), not the *policy* (retry count/backoff), which is not invented here.
- **Feature IDs:** `NOT-001`, `NOT-002`, `NOT-003`.

### 7.2 `Payment`, `Invoice`, `Receipt`, `EMISchedule`, `PaymentWebhookEvent`
**Corrected 2026-09-03 (built alongside `STU-010`/`PAY-001`):** only `Payment` itself carries
over from the inherited codebase — `Invoice`, `Receipt`, `EMISchedule`, and `PaymentWebhookEvent`
did not exist anywhere in code before this feature; this section's original "Carries over" label
was checked directly against the codebase and found wrong for those four. **Ownership:** Student
(self, view), IT Admin/Overseas Admin (view own division).
- **Fields (`Payment`):** `reference_type`/`reference_id` (the inherited codebase's actual
  generic-reference shape, not a fixed `enrollment_id` FK), `provider` (`razorpay`; historical rows
  may still read `stripe` — no backfill/migration performed, existing records are kept as-is per
  `DEC-PAY-001`'s 2026-09-03 re-resolution), `provider_reference`, `amount`, `currency`, `status`
  (`pending`/`paid`/`overdue`, plus whatever a provider webhook reports), `is_manual` (offline/manual
  record, base codebase's retained alternate path, `STU-010-AC02`), `emi_schedule_id`/
  `installment_no` (net-new, groups installment `Payment` rows under one `EMISchedule`),
  `checkout_idempotency_key`/`checkout_provider_order_id` (net-new, `API_CONTRACT.md` §0.2's
  idempotency gate and the webhook's own payment-matching key).
- **`EMISchedule`** (net-new): `user_id`, `division`, `reference_type`/`reference_id`,
  `total_amount`, `currency`, `installment_count`, `created_by_id`. Admin-discretionary — no fixed
  amortization/interest policy is confirmed anywhere, so an Admin supplies each installment's
  amount/due date explicitly rather than the system computing one (same "don't invent an
  unconfirmed business rule" convention as the Agent commission rate).
- **`Invoice`/`Receipt`** (net-new): `payment_id` (unique — one each per `Payment`), `user_id`,
  `division`, `invoice_no`/`receipt_no`, `amount`, `currency`, `file_url`, `issued_at`. An invoice
  is generated as soon as a `Payment` (bill) exists; a receipt once it reaches `paid`/`succeeded`
  (`PRD-PAY-003`). Exact document format/tax breakdown stays open (`PRD_OPEN_ITEMS.md` item 12) —
  only the confirmed fields (amount, currency, payer, reference) are rendered.
- **`PaymentWebhookEvent`:** `provider`, `event_id` (unique — idempotency, see
  `INTEGRATION_CONTRACTS.md` §3), `signature_verified` (boolean — a `Payment` is never marked
  `succeeded` from an event where this is `false`, `PAY-001-AC03`), `raw_payload`, `processed_at`.
- **Multi-currency:** `Payment.currency` and `Invoice.currency` are free per `DEC-PAY-002`'s
  "multi-currency, region unspecified" resolution — no fixed currency list is hardcoded; exact
  supported regions/tax mapping remain open (`PRD_OPEN_ITEMS.md`).
- **Feature IDs:** `STU-010`, `PAY-001`.

### 7.3 `AuditLog`
**Carries over** (already present per `REFERENCE_IMPLEMENTATION_FINDINGS.md` §9 / `SEC-001`).
- **Fields:** `actor_user_id`, `action`, `resource_type`, `resource_id`, `outcome`, `metadata`
  (JSON), `created_at`.
- **Constraint:** a failure to write an `AuditLog` row for a privileged action (Agent approval,
  commission payout approval, GDPR export/delete fulfilment, Super Admin cross-division actions)
  must fail the underlying action itself — fail closed, not open (`SEC-001-AC02`). This is the one
  place in this data model where a write failure is required to be user-visible rather than silently
  retried.
- **Retention:** audit records are retained independently of the resource they describe — an
  `AuditLog` row survives a GDPR delete of the acting user's other data (recorded here as the
  sensible default for legal-evidence purposes; exact retention period is still open, §7.4).
- **Feature IDs:** `SEC-001`, `ADM-014`.

### 7.4 GDPR — `DataExportRequest`, `DataDeletionRequest`
**Net-new**, per `SEC-002`/`NFR-PRIV-001`/`DEC-PRIV-001`.
- **Fields:** `requesting_user_id`, `type` (`export`/`delete`), `status`
  (`received`/`in_progress`/`fulfilled`/`rejected`), `fulfilled_at`, `fulfilled_by_user_id` (nullable
  — self-service vs. Admin-assisted), `rejection_reason` (nullable — e.g. an active legal/financial
  retention hold).
- **Constraint:** a `delete` request is never fulfilled if it would remove data under an active
  retention hold (`SEC-002-AC02`). **What constitutes a retention hold, and exact retention periods
  per data type, are not defined anywhere in evidence** (`DEC-PRIV-001`, `PRD_OPEN_ITEMS.md` item
  15) — this schema records that a hold-check gate exists; it does not invent the hold rules
  themselves. Do not implement automatic period-based deletion until those periods are confirmed.
- **Scope:** an export/delete request only ever touches the requesting user's own data, verified
  server-side (`SEC-002-AC03`) — never trust a client-supplied user ID on this endpoint.
- **Feature IDs:** `SEC-002`.
