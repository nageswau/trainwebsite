## 1. Product vision

A single platform serving EduSphere UK's two current business lines — domestic IT training
(public site, student/trainer/admin operations, CRM-linked enquiries, employer placement) and
Overseas Education consulting (destination/university/course discovery, application, visa, and an
agent referral network with commission) — replacing today's manual coordination between these
processes (BRD §1).

## 2. Goals

Directly from BRD §2, restated as product-level goals:
1. One coherent product for domestic training operations, CRM-linked via Zoho.
2. Employer Portal live in the same release.
3. Overseas Education line live end-to-end: discovery → application → visa → enrolment.
4. Working Agent network with an approval gate and a commission model.
5. Built on a microservices architecture, DigitalOcean-hosted (a delivery constraint on all of the
   above, not a goal in itself).

### 6.1 Domestic admissions handoff (evidence-backed, not independently re-confirmed as a formal
state machine — carried from the blueprint's Academic domain concept, which itself was not a

Enquiry → CRM (Zoho) sync → Admin routing → Student creation/import → Document verification →

### 6.2 Overseas application state machine (`DEC-WF-001` — base sequence CONFIRMED_CURRENT)

**Enquiry/Interest Capture → Eligibility Evaluation → University/Course Selection → Offer
("Unconditional Locker") → Visa Documentation → Status Tracking → Enrolment.**

**CONFIRMED_CURRENT** as the base sequence. **OPEN (not confirmed):** exception paths — rejection,
waitlist, deferral — at any stage; exact system state codes distinct from these stage names. See
`PRD_OPEN_ITEMS.md`.

### 6.3 Agent registration state machine (`DEC-SCOPE-004` — CONFIRMED_CURRENT)

Self-Registration Submitted → **Pending Overseas Admin Approval** → Approved (Active) | Rejected.
An Agent account cannot refer students or view any data while Pending or Rejected.

### 6.4 Agent commission state machine (`DEC-SCOPE-005` — CONFIRMED_CURRENT)

Referral Made → (student's Overseas application reaches Enrolment **and** the student joins the
college) → **Commission Accrued** → Payout Requested → **Overseas Admin Approval** → Paid.
Accrual does **not** occur on offer/acceptance alone — joining the college is required. Payout is a
separate approval gate from accrual. **OPEN:** commission rate/amount — no accrual or payout amount
can be computed without it.

### 6.5 Student trainer/batch enrolment (`DEC-WF-002` — CONFIRMED_CURRENT)

Course Selection → Trainer/Slot Browse (available slots only, capacity-aware) → Slot Selected
(**locked, cannot be changed**, ~3-month duration) → Payment → Active Enrolment.

### 7.1 Identity & Access (cross-cutting)

#### PRD-AUTH-001 — Authenticated login, single identity across domestic and Overseas
- **Source:** `DEC-ROLE-001`
- **Actor:** Student (incl. Overseas applicant)
- **Requirement:** A Student authenticates once and accesses both domestic learning features and
  Overseas application features under the same account.
- **Business rule:** Overseas applicant data is an extension of the Student profile, never a
  separate account.
- **Preconditions:** Account exists (self-registered or admin-created).
- **Main behavior:** Successful login grants access to whichever of Student/Overseas-applicant
  capabilities apply to that account's data.
- **Error/edge behavior:** A Student with no Overseas application data sees no Overseas-specific UI
  (not an error — an empty/absent state).
- **Security/privacy:** Session must not leak one identity's data to another; standard
  authenticated-session handling.
- **Acceptance direction:** A single login grants access to whichever domestic/Overseas capabilities
  apply, with no second account or second login required.
- **Scope/status:** CONFIRMED_CURRENT

#### PRD-AUTH-002 — Role-based access control
- **Source:** BRD §5 roles table; blueprint's role-bundle concept (PROPOSED structure, roles
  themselves CONFIRMED via Decision Register)
- **Actor:** All roles
- **Requirement:** Each role sees and acts only within its own permitted capability set (Visitor,
  Student, Trainer, Admin incl. Overseas Admin, Employer, Agent).
- **Business rule:** Overseas Admin is the specific approval authority for Agent registration and
  commission payout — not any Admin.
- **Preconditions:** Authenticated session with a resolved role.
- **Main behavior:** UI/action availability reflects role; attempts outside the role's capability
  are refused.
- **Error/edge behavior:** An action attempted outside role scope is rejected, not silently ignored
  or partially applied.
- **Security/privacy:** This is the primary access-control boundary for every other requirement
  below — every FR in this document inherits it.
- **Acceptance direction:** No role can perform an action reserved for another role, verified per
  role pairing.
- **Scope/status:** CONFIRMED_CURRENT (roles); PROPOSED (unconfirmed) for the exact Admin sub-bundle
  split (Content/Operations/Finance/Super) — that split is blueprint-only, never independently
  re-confirmed.

#### PRD-AUTH-003 — Google login option
- **Source:** EVID-010 (TECH_STACK_PREFERENCE, "JWT with Google login") — **not independently
  re-confirmed** via the Decision Register during this session
- **Actor:** Student, Trainer, Admin, Employer, Agent
- **Requirement:** Users may authenticate via Google in addition to standard credentials.
- **Scope/status:** PROPOSED (unconfirmed) — carried from original tech-stack evidence; not asked

### 7.4 Trainer

#### PRD-TRN-001 — My Batches
- **Source:** EVID-008 ("it will show him how many batches are assigned to him right now"),
  `DEC-ROLE-002`
- **Actor:** Trainer
- **Requirement:** A Trainer sees a list of all batches currently assigned to them ("My Batches").
- **Business rule:** A Trainer sees only their own assigned batches, not the full batch list
  (that's Admin's view, `PRD-ADM-003`).
- **Preconditions:** At least one batch assigned by Admin.
- **Main behavior:** List shows each assigned batch with enough summary to identify it (course/

- **Error/edge behavior:** No batches assigned yet → empty state, not an error.
- **Security/privacy:** Scoped strictly to the authenticated Trainer's own assignments.
- **Acceptance direction:** Every batch a Trainer is assigned to (and no others) appears in this

- **Scope/status:** CONFIRMED_CURRENT

#### PRD-TRN-002 — Batch detail (roster and schedule)
- **Source:** EVID-008 ("this is the [furthest] batch, the schedule was on Monday, Wednesday,
  Friday, seven IST, the status is active"), `DEC-WF-002`
- **Actor:** Trainer
- **Requirement:** Opening a batch from "My Batches" shows its student roster and its schedule
  (days/time, status).
- **Business rule:** Roster reflects the confirmed enrolment model — students who selected this
  specific trainer/slot (`DEC-WF-002`), capped at 20.
- **Preconditions:** Batch exists and is assigned to this Trainer.
- **Main behavior:** Roster + schedule + status (e.g. active) are shown together for the batch.
- **Security/privacy:** Roster is scoped to that batch only — a Trainer does not see students from
  other trainers' batches.
- **Acceptance direction:** Batch detail shows exactly the students enrolled in that batch's slot,

- **Scope/status:** CONFIRMED_CURRENT

- **Scope/status:** CONFIRMED_CURRENT (requirement); OPEN (exact join-link update cadence —

- **Requirement:** An Agent requests ("claims") payout of accrued commission; a **separate**
  Overseas Admin approval step is required before it is marked paid.
- **Business rule:** **Extends existing code.** The reference implementation already has an agent
  "claim" action (`eligible`/`estimated` → `claimed`, with a generated `claim_reference` and

  moves a claimed commission to paid**, and critically, no approval gate between claim and payment.

  in `DEC-SCOPE-005`.
- **Error/edge behavior:** An Agent cannot mark their own commission paid — only Overseas Admin can,
  via the new approval action.
- **Acceptance direction:** No commission reaches `paid` status without an explicit, separate
  Overseas Admin approval action distinct from the Agent's own claim.
- **Scope/status:** CONFIRMED_CURRENT (mechanism, extending existing code); OPEN (the exact
  application-status value/event that should fire the automatic trigger in `PRD-AGT-003` — only one
  status transition, `profile_evaluation → university_review`, was observed in the codebase's own
