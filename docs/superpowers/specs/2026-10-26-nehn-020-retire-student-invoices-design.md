# nehn-020 — Retire student-facing invoices (design)

**Source:** `docs/delivery/CONSOLIDATED_REVIEW_ENHANCEMENT_BACKLOG.md` `nehn-020` (§7 L167-168, "invoice functionality can be removed
where not required"; `UNVERIFIED` backlog). Decision: `DEC-SCOPE-289`. Owner pre-authorised the recommended answers; open questions are
recorded as `NEEDS_CONFIRMATION`, not resolved.

## Intent

The receipt is the student's payment document. A student should not be offered, or be able to fetch, an invoice.

## Current state (verified 2026-10-26)

- Invoices are generated by `_ensure_invoice` (`api/payments.py`) at checkout, at enrolment (`workflows.py`), on an admin discount or EMI
  change (`admin.py`) and for agent deposits (`agent_deposits.py`).
- Students download one from the **Invoice** button in `FeePaymentPanel` (it_student *Fees*, overseas_student *Payments*), served by
  `GET /payments/{id}/invoice` (owner, or an admin in the payment's division).
- The invoice rows are read elsewhere: the Accounts dashboard's **pending invoices** KPI (AD6, `services/accounts.py`) counts fee
  invoices of unpaid payments, and the Overseas Admin downloads invoices from the counselor 360 finance tab (ccrm-039).

## Design (builder's calls)

| # | Call | Why |
|---|---|---|
| I1 | Remove the **Invoice** button from `FeePaymentPanel`; the **Receipt** button and its behaviour are unchanged. | AC1. |
| I2 | `GET /payments/{id}/invoice` returns **404** "Invoices are not issued to students. Download your receipt instead." when the caller is an `it_student`/`overseas_student`. Checked **after** the existing ownership check, so another student's payment is still 403. | AC1 at the API, not just hidden in the UI. 404 (not 410): the route already uses 404 for "no document for you"; 410 would claim a resource that existed for this caller. |
| I3 | Admins (own division; super_admin all) and agents (payers of `agent_deposit`) keep the route unchanged. | AC3, and agents are not students. |
| I4 | **Generation is unchanged** — no `_ensure_invoice` call site is removed. AC2's "removed contexts" is the empty set until OD-11 (is a GST/tax invoice legally required?) is answered. | Rows feed AD6 and admin history; removing generation is irreversible for the gap period, hiding is not. `NEEDS_CONFIRMATION` (OD-11). |
| I5 | No migration, no data change; historical invoices stay. | Backlog: keep the data. |

**Alternatives rejected:** removing the `_ensure_invoice` call sites (breaks AD6, pre-empts OD-11); a feature flag (an abstraction for a
one-way product choice); 410 Gone (see I2).

## Acceptance criteria (testable)

1. A student's fee card shows no Invoice button; a paid fee still shows Receipt. *(vitest, e2e)*
2. A student calling `GET /payments/{own id}/invoice` gets 404 with the message above; on another student's payment, 403. *(pytest)*
3. An admin in the payment's division still gets 200 and a URL for a historical invoice. *(pytest)*
4. Checkout still creates the invoice row (generation unchanged, I4). *(pytest)*

## Review notes (Phase 3)

- **API:** behaviour change limited to student callers on one route; response shape unchanged for everyone else. Documented in API §12GN.
- **Security:** no new data exposure; the 403 for non-owners is preserved; no IDOR change; no logging of document keys.
- **Frontend:** removing a button from an existing flex row; no new state. The download helper narrows to receipts.
- **Regression risks:** tests that fetch the invoice as a student (`test_pay_001_stu_010_payment_gateway.py`, `pay-001-stu-010`
  e2e) — updated to the new rule.

## Out of scope

nehn-019 (receipt content, discount ledger); invoice PDF format/GST; agent and admin invoice screens.
