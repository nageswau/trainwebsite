## 1. Certificate public-verification conflict (explicitly requested audit)

**Confirmed and reproduced with hard evidence.** `API_Catalogue` correctly marks
`API-CERT-001` (`GET /api/v1/certificates/verify/{code}`) as `Allowed Roles: Public`. Its three
generated test cases contradict that:

| Case | Defect |
|---|---|
| `API-238` | Step 1 instructs "Send GET request... **with valid authentication**" — wrong for a Public endpoint. |
| `API-239` | Titled "enforces authentication, authorisation and resource scope"; asserts 401 without credentials, 403 for a disallowed role, 404/403 for a mismatched owner — **all three assertions are wrong for a Public, ownerless verification lookup.** |
| `API-240` | Titled "handles validation, filtering and pagination boundaries"; asserts default pagination, page-size bounds, empty-page metadata — **wrong for a single-resource-by-code lookup, which is not a list.** |

**Classification:** `API-238`→`REWRITE` (drop the auth precondition), `API-239`→`REWRITE` (invert to
assert public accessibility + abuse/rate-limit protection instead of 401/403), `API-240`→`SPLIT`
(replace with a validation/not-found case: malformed code → 400/422, nonexistent code → 404 or a
"not verified" result per product decision, no pagination assertions). See `TEST_REWRITE_PLAN.md` §1
for the corrected case set.

## 2. Public content auth conflict (explicitly requested audit)

The generic API template `"<endpoint> enforces authentication, authorisation and resource scope"`
(applied uniformly to all 107 `API Functional`-paired `API Security` cases) was cross-referenced
against `API_Catalogue`'s `Allowed Roles` column. **13 cases** apply this 401-without-credentials
template to an endpoint explicitly marked `Public`:

`API-002` (`POST /auth/login`), `API-005`/`API-008` (Google OAuth start/callback — also `BLOCKED`,
§4), `API-017`/`API-020` (password forgot/reset), `API-035`/`API-038` (public course catalogue),
`API-137` (employer registration), `API-161` (public enquiry), `API-164` (public webinar
registration), `API-239` (certificate verify, §1), `API-251` (public CMS content), `API-296`
(`/health/live`).

**Classification:** all 13 → `REWRITE`. Several of these (login, password reset, health check) are
*intentionally* unauthenticated by design — the corrected case should assert the endpoint **remains
reachable without credentials** and instead test the controls that actually apply (rate limiting,
generic error messages for no-enumeration, input validation) rather than a contradictory 401 check.

## 3. Payment/provider webhook authentication semantics (explicitly requested audit)

5 webhook-related cases found. Only `API-224` (`POST /payments/webhooks/{provider}` — "enforces
authentication, authorisation and resource scope") applies the wrong frame: a provider webhook
authenticates via **signature verification**, not user role/session — 401-without-credentials,
403-wrong-role, and 404-wrong-owner are not meaningful checks for a system-to-system callback.

`SEC-022` ("Webhook signature, replay and idempotency," Security suite) already has the **correct**
frame and substantially overlaps `API-223`/`224`/`225`'s intended coverage.

**Classification:** `API-224` → `MERGE` into `SEC-022` (rewritten to name Razorpay explicitly
per `DEC-PAY-001`'s 2026-09-03 re-resolution — sole payment provider, Stripe removed — and cite
`INTEGRATION_CONTRACTS.md` §2's signature-verification/idempotency contract). `API-223` (successful-
response contract) and `API-225` (payload validation/duplicate protection) → `KEEP`, retrace to
`PAY-001`. `PERF-009` (webhook burst) → `KEEP`, retrace to `PAY-001`.

**Additional finding beyond the named categories:** the CRM webhook (`PUB-002`/`ADM-002`, Zoho) and
the Twilio WhatsApp status-callback (`INTEGRATION_CONTRACTS.md` §4) have **zero existing webhook-
auth test coverage** in the old catalogue — carried into `COVERAGE_GAPS.md`.

## 6. Vague "where applicable" (explicitly requested audit)

**326 of 824 cases (40%)** contain at least one instance of exactly **4 distinct template phrases**,
applied mechanically rather than case-specifically:
1. `"Zoom to 200% and rotate device where applicable"` (Responsive/Accessibility template)
2. `"Repeat read or safe retry where applicable"` (API Functional template — see §7)
3. `"Cause a concurrent update using an old version/ETag where applicable"` (API Validation template
   — see §7; **zero cases in the entire catalogue define an actual ETag mechanism**, so "where
   applicable" here silently means "never, since no ETag contract exists")
4. `"Repeat after tuning or failure injection where applicable"` (Performance template)

This is not four independent judgment calls per case — it's the same four strings copy-applied
across hundreds of cases regardless of whether the underlying endpoint/screen makes the condition
meaningful. **Classification:** does not by itself force a bucket (several affected cases are
otherwise sound `KEEP`s), but every `REWRITE` case that also carries one of these phrases (§7, §8)
must resolve the hedge to a concrete yes/no per the specific endpoint's actual contract, not restate
"where applicable."

## 7. Uncontracted idempotency assumptions (explicitly requested audit)

**All 107 of 107** `API Functional` cases (100%) carry the identical step: *"Repeat read or safe
retry where applicable... idempotency rules prevent duplicates for mutating operations."*
Cross-referencing against `API_Catalogue` method:

- **50 of 107** are `GET` (read-only) endpoints — for these, "prevent duplicates for mutating
  operations" is **nonsensical**; a GET has no mutation to duplicate. `REWRITE` to a genuine
  read-repeatability assertion instead.
- **57 of 107** are mutating (`POST`/`PUT`/`PATCH`/`DELETE`) endpoints — for these, the assertion is
  directionally relevant but **uncontracted**: `API_CONTRACT.md` §0.2 requires an `Idempotency-Key`
  only on specific financial/state-creating endpoints (checkout session creation, commission claim,
  GDPR request submission) — not on every mutation. `REWRITE` each to either (a) cite the actual
  `Idempotency-Key` contract if the endpoint is one of the few that has one, or (b) drop the
  assertion entirely if it isn't.

**Total: 107 `REWRITE`** (all of §7 already counted in the 165 `REWRITE` total, not double-counted
against §2/§5).

## 8. Uncontracted ETag assumption (related finding, folded into §6/§7)

The `"...old version/ETag where applicable"` phrase appears in the `API Validation` template but
**no endpoint in `API_CONTRACT.md` specifies an ETag/optimistic-concurrency mechanism anywhere** —
this project never designed one (no confirmed requirement called for it). Every case carrying this
phrase should have it removed or replaced with a genuine concurrent-write test appropriate to the
endpoint (e.g. a database-level constraint check), not an ETag assertion against a contract that
doesn't exist.

The three-case-per-endpoint template (`API Functional` / `API Security` / `API Validation`, one each
per `API_Catalogue` row) is itself a reasonable, non-duplicative pattern **once corrected per §2/§5/
§7** — flagged here only to confirm it was checked, not found duplicative beyond the specific defects
already listed above.

## 10. Missing BOLA/IDOR/resource-scope checks (explicitly requested audit)

The old catalogue's `RBAC_Matrix` sheet lists only **8 roles** (Visitor, Student, Trainer, Employer,
Admin-Content, Admin-Operations, Admin-Finance, Admin-Super) — **no Overseas-division role at all**
(no Counselor, Agent, University Representative, Overseas Admin, Overseas Student distinction), and
no Placement Team/HR Team split. This independently confirms (a third, structural piece of evidence
alongside §12) that the old catalogue's BOLA/IDOR coverage (`SEC-008`/`009`/`010`, generally
well-designed as generic checks) was never exercised against the resource-scope rules this project's
`RBAC_MATRIX.md` actually requires: Trainer-own-batch-only, Counselor-assigned-students-only,
University-Rep-own-institution-only, Agent-own-referrals-only, Employer-own-postings-only. **Zero
existing cases test these specific scope boundaries** — carried into `COVERAGE_GAPS.md` and
`TEST_REWRITE_PLAN.md` §4 as net-new cases.

  labels, screen reader, contrast, zoom/reflow, media captions) but written against the old,
  smaller screen set — none reference Overseas/Employer/Agent screens (net-new or restructured
  since the workbook was authored). `KEEP` the 7 generic cases; **gap:** no accessibility case
  exists yet for any Overseas/Employer/Agent screen. `NFR-A11Y-001` itself is `PROPOSED`
  (unconfirmed conformance level) — do not assert a specific WCAG level as a hard gate until
  confirmed.
- **Integration:** only 5 cases (`INT-001`–`005`) for the *entire* provider surface. `INT-001`
  (Zoom/Teams) → `RETIRE` (contradicts `DEC-LIVE-001`, confirmed Zoho Meeting/Google Meet).
  `INT-005` (External LMS) → `RETIRE` (contradicts `DEC-LMS-001`, confirmed native build). `INT-002`
  (Email), `INT-003` (WhatsApp) → `KEEP`/`REWRITE` (retarget WhatsApp to Twilio by name). `INT-004`
  (GitHub) → `RETIRE` (no traceable requirement anywhere in evidence). **Gap:** zero integration
  cases for Zoho CRM webhook, Zoho Meeting, Razorpay, Twilio SMS, or DigitalOcean Spaces —
  every one of this project's actually-confirmed providers. See `COVERAGE_GAPS.md` §3.
- **UAT:** 4 cases (Student/Trainer/Admin/Employer journeys) — reasonable base but **zero** for an

- **Performance/Reliability:** 25 cases, generally well-structured, but two systemic issues:
  (a) several implicitly gate on `NFR-PERF-001` (2s response) and `NFR-REL-001` (uptime), both
  `PROPOSED`/`OPEN` (unconfirmed) in `PRD.md` §8 — `REWRITE` to record-and-report, not hard

  `DEC-INFRA-001` superseded with DigitalOcean — `REWRITE` to retarget per `ADR-003`/`004`.

## 12. Total scope-coverage gap — the Overseas Education domain

Independently confirmed **three separate ways**: (1) zero test cases anywhere match the keywords
overseas/visa/agent/commission/counsel/university-rep/scholarship; (2) zero of the 303 distinct

`UNI-001` Feature ID (18 `CURRENT` features) needs entirely new test cases — see `COVERAGE_GAPS.md`
§1 and `TEST_REWRITE_PLAN.md` §4.
