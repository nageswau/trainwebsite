## 1. Worked example — certificate public verification (`API-238`/`239`/`240`)

**Old (defective):**
- `API-238`: requires "valid authentication" on a Public endpoint.
- `API-239`: asserts 401/403/404 role-and-ownership checks on an ownerless public lookup.
- `API-240`: asserts pagination/filter/sort boundaries on a single-resource-by-code lookup.

**Rewritten (3 cases, replacing all 3 old ones):**

| New ID | Type | Title | Key assertions |
|---|---|---|---|
| `API-CERT-VER-01` | API Functional | `GET /certificates/verify/{code}` returns the documented result, no auth required | Valid code → 200 with verification result (issued-to, course, issue date, status); request succeeds with **no** `Authorization` header present — confirms `API_CONTRACT.md` §2's Public marking. |
| `API-CERT-VER-02` | API Validation | `GET /certificates/verify/{code}` handles malformed/nonexistent codes | Malformed code format → 400/422 with a clear `field_errors` message. Well-formed but nonexistent/revoked code → a defined "not verified" result (200 with `status=not_found` or `revoked`, per `DATA_MODEL.md` §4.7 — **not** a 404 that would let an attacker distinguish "malformed" from "doesn't exist" if that distinction matters; confirm exact contract before finalizing). No pagination/filter/sort assertions — this is a single-resource lookup. |
| `API-CERT-VER-03` | API Security | `GET /certificates/verify/{code}` resists abuse without requiring auth | Rate-limiting/abuse-protection behavior on a public, unauthenticated, enumerable-by-code endpoint (a real risk this endpoint's public nature introduces — code-guessing) — the correct security concern for this endpoint, replacing the wrong 401/403 template. |

Traces to `STU-007` (issuance) and the public verification capability implied by `ADM-006`'s
certificate administration. Feature ID for the **public verification endpoint itself** is not
independently named in `MASTER_FEATURE_CATALOG.md` (only `STU-007`/`ADM-006` cover issuance/download)
— **flagged as an open item**: confirm whether public certificate verification is in current scope at
all before finalizing this rewrite; the old workbook assumed it was (`API-CERT-001`), but no PRD/BRD
item in this project's own evidence independently confirms it. Carry into `PRD_OPEN_ITEMS.md`.

## 2. Worked example — public-content auth template fix (pattern, applies to all 13 cases in `TEST_CATALOG_AUDIT.md` §2)

**Old pattern:** "Call {endpoint} without credentials → 401. Call with expired credentials → 401.
Call with a disallowed role → 403. Call with another user's resource ID → 404/403."

**Rewritten pattern for a `Public`-role endpoint:**
1. Call without credentials → succeeds (matches `API_CONTRACT.md`'s documented success response) —
   confirms Public access is real, not accidentally gated.
2. Call with a valid session from an authenticated role → still succeeds identically (no
   inconsistent behavior between anonymous and authenticated callers on a genuinely public
   endpoint).
3. Replace the removed 403/404 ownership checks with the actual applicable control for a public
   endpoint: input validation (malformed payload → 400/422) and, where the endpoint is
   write-capable (enquiry submission, webinar registration, employer registration), basic
   abuse-resistance (e.g. obvious bot/spam pattern handling) per `SECURITY_CONTROLS.md` §1's rate-
   limiting recommendation.

Apply this pattern to: `API-002`, `API-017`, `API-020`, `API-035`, `API-038`, `API-137`, `API-161`,
`API-164`, `API-251`, `API-296` (10 cases; `API-005`/`API-008` are `BLOCKED` per §4 below, `API-239`
is superseded by §1).

## 3. Worked example — idempotency template fix (pattern, applies to 107 `API Functional` cases)

**Old step (uniform, all 107 cases):** *"Repeat read or safe retry where applicable... idempotency
rules prevent duplicates for mutating operations."*

**Rewritten, GET (read) endpoints (50 cases):** replace with *"Repeat the same GET request twice in
succession → identical response both times (safe, naturally idempotent); no server-side state
changes as a side effect of a read."*

**Rewritten, mutating endpoints (57 cases) — two sub-patterns:**
- **Endpoints requiring an `Idempotency-Key`** per `API_CONTRACT.md` §0.2 (checkout-session
  creation, commission claim, GDPR request submission — currently 3 endpoint families): *"Submit the
  same request twice with the same `Idempotency-Key` → second response returns the first result
  without creating a duplicate record. Submit with a different key → processes as a new request."*
- **All other mutating endpoints (the remaining ~54 of 57):** drop the idempotency assertion
  entirely — replace with the endpoint's actual duplicate-prevention behavior where one exists at
  the data-model level (e.g. `OVS-002`'s unique-application constraint, `DATA_MODEL.md` §6.2), or
  omit the step if no such constraint is contracted. **Do not assert generic idempotency where no
  contract requires it** — this is exactly the "uncontracted assumption" this audit exists to catch.

## 8. Traceability check

Every new case stub above cites a `CURRENT` Feature ID and, where applicable, the specific `-AC0#`
it verifies, plus the contract document (`DATA_MODEL.md`/`API_CONTRACT.md`/`RBAC_MATRIX.md`/
`INTEGRATION_CONTRACTS.md`/`SECURITY_CONTROLS.md`) it is grounded in. No stub invents business
behavior beyond what those approved documents already specify — where a contract itself flagged an
open item (e.g. certificate-verification's own Feature-ID gap, §1), the test stub inherits that same
flag rather than resolving it silently.
