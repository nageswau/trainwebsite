## 1. Why the old catalogue is input to an audit, not authority

Per `CLAUDE.md`: *"The workbook contains 824 tests, all marked Draft. Treat them as input to an
audit, not authority. Never alter product behavior merely to make a draft test pass."* The workbook
was generated against an **earlier, different scope** than the one now confirmed: it predates the
Zoho CRM webhook decision, the confirmed Employer net-new build, the entire Overseas Education domain
(destinations/applications/visa/agent/commission/counselor/university-rep — `DEC-SCOPE-003`–`006`),
the DigitalOcean infrastructure decision, the native-LMS decision, and the GDPR/audit contracts this
project designed in `prompts/09`. Treating it as authoritative would silently reintroduce scope the
Decision Register explicitly excluded or changed. This audit checks every case against the
**approved** contracts, not the reverse.

## 2. Method — how 824 cases were audited without loading them all into one context

Per `CLAUDE.md`'s token-efficient-operation rule and this prompt's own instruction ("do not load all
824 cases or 3,161 steps into one context"):

1. The original `.xlsx` was **read programmatically** (Node.js `xlsx` library, run locally in the
   scratch workspace) — never modified, per the prompt's explicit rule.
2. Compact summaries were computed first: sheet dimensions, Suite/Test-Type/Status breakdowns,
   distinct Requirement-code counts — before reading any individual case content.
3. Targeted, evidence-driven queries pulled only the specific rows relevant to each known bad-pattern
   category (typically 5–30 rows at a time), which were the only rows read in full (Title + all
   steps) directly in-session.
4. A **rule-based classifier script** (not manual one-by-one review) applied documented, evidence-
   backed rules to all 824 cases programmatically, cross-referencing each case's `Requirement /
   Screen / API` column against `API_Catalogue` (for method/path/allowed-roles) and against the
   approved `MASTER_FEATURE_CATALOG.md` Feature ID families. Full results: `test_audit.json`.
5. Aggregate counts and named examples (not the full 824-row listing) are what appear in
   `TEST_CATALOG_AUDIT.md` — consistent with "inspect compact summaries first... open detailed
   [records] only for failures/specific review."

This method is auditable (every rule cites its evidence and every classified case is in
`test_audit.json`) without requiring the full catalogue to pass through model context at once.

## 3. Classification taxonomy

| Label | Meaning |
|---|---|
| `KEEP` | Content is sound and reusable as-is; only the `Requirement / Screen / API` trace needs updating to point at the correct new Feature ID/AC. |
| `REWRITE` | Content has a specific, named defect (wrong auth frame, uncontracted assertion, unconfirmed NFR gated as pass/fail, stale provider name, etc.) that must be corrected before reuse. |
| `SPLIT` | A single case bundles assertions that don't belong together (e.g. a pagination assertion incorrectly bundled with a single-resource validation case) — divide into separate, correctly-scoped cases. |
| `MERGE` | Two or more cases duplicate coverage that belongs in one case once corrected. |
| `RETIRE` | The case tests behavior that **contradicts a confirmed Decision ID** or has no traceable requirement anywhere in current evidence — remove rather than rewrite. |
| `BLOCKED` | The case traces to a Feature ID that is itself `BLOCKED` in `MASTER_FEATURE_CATALOG.md` (unconfirmed PRD item) — no AC exists to test against yet; retained as a specification for when unblocked, not executed. |

**Test count is never used as quality proof** (`prompts/10`'s own rule) — the summary in
`TEST_CATALOG_AUDIT.md` reports classification distribution and named defect categories, not a raw
count as a success metric.

## 4. Traceability rule for every retained/new test

Every retained or newly-added test case must trace: **PRD/NFR → Feature ID → AC → contract/screen**,
per the prompt's own requirement. Concretely: the `Requirement / Screen / API` column must cite a
current Feature ID (e.g. `STU-001`) and, where the case exercises a specific acceptance criterion, the
`-AC0#` it verifies (e.g. `STU-001-AC02`). API-suite cases additionally cite the endpoint from
`API_CONTRACT.md`; RBAC/security cases cite the specific grant/deny row in `RBAC_MATRIX.md`.

## 5. Naming-hygiene note (new finding, not previously flagged)

The old workbook's own `Case ID` scheme includes a `SEC-001`…`SEC-039` range (Security suite) that
**collides textually** with this project's Feature IDs `SEC-001` (Approval-gate audit trail) and
`SEC-002` (GDPR). They are unrelated (the workbook's `SEC-001` is "Brute-force and credential-stuffing
protections"). This is not a defect in either document, but it is a legibility risk once both are
referenced side-by-side in the rebuilt catalogue. **Recommendation:** prefix rebuilt test-case IDs
distinctly from Feature IDs (e.g. retain `SEC-0xx` as a Security-suite case-ID range but always write
the Feature-ID trace out in full, e.g. `Feature: SEC-002`, never bare `SEC-002` where it could be
misread as the test case ID). Not a blocking issue — flagged for the rebuild pass.

## 6. What "rebuild" means here

Per `prompts/10`, this phase produces the **audit and the rewrite plan**, not the rewritten test
suite itself in full (824 rewritten cases would itself be a large, code-adjacent artifact better
produced per-feature during `prompts/13_FEATURE_LOOP.md`, where each feature's tests are written
alongside its implementation). `TEST_REWRITE_PLAN.md` gives the concrete plan, worked examples for
every named defect category, and net-new test stubs for confirmed coverage gaps (Overseas domain,
GDPR specifics, commission two-gate, provider-specific integration contracts) — sufficient to execute
against without re-auditing, but not a full 824-case rewritten workbook.
