# Feature Questions

Generated by `prompts/06_MASTER_FEATURE_CATALOG.md`. Questions surfaced specifically by decomposing
PRD requirements into buildable features — narrower than `docs/product/PRD_OPEN_ITEMS.md` (52 items,
still all open and not repeated here) but blocking at the feature/AC level.

## New, feature-decomposition-specific questions

1. **Employer ↔ Placement Team/HR Team coexistence** (blocks `EMP-002` AC refinement). The
   reference implementation handles corporate hiring entirely through internal `placement_team`/
   `hr_team` staff. The new `Employer` role (`EMP-*`) is being built alongside that model, but
   *how they interact* is undefined: does a Placement Team member need to approve/mediate an
   Employer-posted job before it's visible to Students, or does Employer post directly with
   Placement Team only seeing it in their existing `candidates`/`company-requirements` view? First
   raised in `docs/product/ROLE_ACTION_MATRIX.md`.

2. **Ops-tooling cluster ownership** (blocks `ADM-013`, keeps it `BLOCKED`). Audit logs, backups,
   system settings, security logs exist in the base codebase under **Super Admin**
   (`docs/product/ROLE_ACTION_MATRIX.md` §Super Admin, `ADM-014`), but PRD's own
   `PRD-ADM-012` proposed them as an **IT Admin** capability. Which role actually owns this? Also
   first raised in `ROLE_ACTION_MATRIX.md`.

3. **Division-pinned identity vs. "same Student identity"** (affects `STU-001`/`OVS-002`/`AUTH-001`
   design, doesn't block build but should be resolved before Contracts). `DEC-ROLE-001` confirmed
   one Student identity spans both divisions; the base codebase pins every user to exactly one
   division with separate `it_student`/`overseas_student` role values. Does one person hold both
   role-assignments simultaneously under one account, or does the base model need adjusting?

4. **Commission auto-trigger status mapping** (blocks precise `AGT-003` AC, tracked already as
   PRD open item 50). `OverseasApplication.status` has no observed "joined" terminal state in the
   base codebase's own seed data — only `profile_evaluation → university_review` was seen. The
   actual status value that should fire the automatic commission trigger needs to be designed, not
   assumed, in `prompts/09` (Contracts).

5. **Payout-approval endpoint** (tracked already as PRD open item 51, `AGT-004`). Genuinely new API
   surface — the base codebase has no `claimed → paid` endpoint at all. Confirm this is Contracts-
   phase work, not something to reverse-engineer from elsewhere in the codebase first (a search
   beyond `workflows.py`'s agent-commission section was not performed — worth a final check before
   Contracts starts, in case it exists elsewhere, e.g. under `admin/payments`).

6. **PRD backfill for `[base]` role actions.** 9 features (`ADM-007`, `ADM-008`, `ADM-014`,
   `CNS-001`, `UNI-001`, `PUB-005`, `NOT-003`) trace to `DEC-ARCH-001` (extend the reference
   implementation) rather than an independently-authored PRD requirement, per
   `FEATURE_TRACEABILITY.md`'s partial-traceability flag. This is a legitimate trace under the
   prompt's own rules (a Decision ID is sufficient), but it means these actions were never
   individually reviewed against evidence the way every `PRD-*`-sourced feature was. Worth a
   lightweight PRD amendment pass at some point — not blocking, but noted so it isn't forgotten.

7. **Employer-approval workflow** (blocks `EMP-001` AC precision — already PRD open item 2/32).
   Does a new Employer account need Admin approval before activation? Neither the blueprint (which
   raised this as its own unresolved item #28) nor the base codebase (which has no Employer concept
   at all) answers it.
