# MVP Features

Generated by `prompts/06_MASTER_FEATURE_CATALOG.md`. **No client-confirmed MVP subset exists.**
Per `docs/product/BRD.md` §6.2, every scope decision in this project landed as `CONFIRMED_CURRENT`
or `OUT_OF_SCOPE` — none as `CONFIRMED_FUTURE`. Combined with BRD Risk R-01 (the confirmed release
date is 4 days out against the full scope), this project has a real, unresolved mismatch between
"everything is current release" and "there is no credible timeline for everything."

**What follows is a recommendation, not a decision** — proposed specifically because the
alternative (silently treating all 68 CURRENT features as equally first-wave) would make the
timeline problem worse, not better. This needs explicit user confirmation before
`prompts/11_IMPLEMENTATION_PLAN_AND_RELEASE_BACKLOG.md` treats it as real.

## Recommended MVP (proposed — Wave 0 + Wave 1, 27 features)

The smallest slice that delivers one complete, real business loop end-to-end: a Visitor becomes a
Student, enrols with a Trainer, pays, learns, and an Admin can run the domestic operation. This
excludes Overseas/Agent/Employer entirely — not because they're less important, but because they
are the newest, least-specified domains (see `BACKLOG_GAP_ANALYSIS.md`, `FEATURE_QUESTIONS.md`) and
bundling them into a first slice maximizes risk, not minimizes it.

**Wave 0 — Foundation (4):** `FND-001`, `FND-002`, `OPS-001`, `OPS-002`

**Wave 1 — Domestic core loop (23):** `AUTH-001`, `AUTH-002`, `PUB-001`, `PUB-002`, `PUB-003`,
`STU-001`, `STU-002`, `STU-003`, `STU-004`, `STU-009`, `STU-010`, `TRN-001`, `TRN-002`, `TRN-003`,
`TRN-005`, `TRN-007`, `TRN-008`, `ADM-001`, `ADM-002`, `ADM-003`, `ADM-005`, `PAY-001`

This alone is not trivial — it's still real/full-stack work extending an existing modular monolith
across auth, RBAC, enrolment with capacity/lock-in rules, live-class integration, payment webhooks,
and admin CRUD. It is offered as the *minimum* credible MVP, not a small one.

## Explicitly NOT in the proposed MVP (would need separate confirmation to pull forward)

- **Overseas/Visa/Agent** (`OVS-*`, `VISA-*`, `AGT-*`, `CNS-001`, `UNI-001`) — 16 features. This is
  a materially newer, less-specified business line (BRD Risk R-07: rests on one informal
  transcript). Pulling it into MVP without further specification (`FEATURE_QUESTIONS.md`) risks
  building the wrong thing twice.
- **Employer** (`EMP-*`) — 6 features, all net-new build with no base-codebase equivalent.
- **Reporting** (`RPT-*`), **native LMS extensions** (`LMS-001`), **notification breadth beyond
  Email** (`NOT-002`/`NOT-003`), **Super Admin console** (`ADM-014`) — lower-priority or
  cross-cutting enhancements to the core loop, not required for it to function.
- All 10 `BLOCKED` features (see `MASTER_FEATURE_CATALOG.md`) — not authorized to build regardless
  of MVP status, pending PRD confirmation.

## What this recommendation does NOT do

It does not resequence anything in `docs/product/PRD.md` or `docs/product/BRD.md`, and it does not
change any feature's `scope` field in the catalogue (Overseas/Employer/Agent remain `CURRENT`, not
`FUTURE`) — MVP here is a proposed *build order*, not a scope change. If the user wants
Overseas/Agent pulled into a true first wave instead (e.g. because it's the newer, growth-driving
line of business), that's an equally valid call — it just needs to be made explicitly, not defaulted
to by whichever order this document happened to list things in.
